# Runtime ownership

Optional trusted host storage initialization runs after exclusive ownership and SQLite setup, before provider registry, action controllers, Claude observation, IPC or native warm-up/rejoin exist. Its callback receives a copied descriptor and owns its connection, transaction and rollback. Startup failure uses the existing worker/ownership cleanup and preserves the original callback error when cleanup succeeds. Retained native Codex execution can continue independently without a second input or native event writer in this phase. Live storage maintenance keeps its active-native-execution refusal. No additional cache is useful for a once-per-start correctness boundary.

Completed controlled Codex async questions cross the trusted `observeAsyncInputs` boundary after their managed source is resolved. The in-process subscription holds only callbacks, supplies independent item copies, and isolates synchronous listener failures with recovery signals. It keeps no event queue, transcript bodies or durable question state. Hosts synchronously enqueue bounded persistence/recovery work and use native history for catch-up after subscription, connection loss or output gaps. Structured question bytes count toward live-memory and evidence-response bounds; saved/live reconciliation compares the complete metadata. Async messages never enter ordinary final-result capture. This additive contract preserves schema 12.0.1 and existing action keys.

## Providers

Usage observations remain owned by the selected native adapter. Concurrent reads share its pending refresh; failed refreshes retain explicitly stale observations, and account changes discard all quota, credit and reset metadata. The Claude adapter keeps its last result in memory for 60 seconds, so frequent usage polls ask Claude at most once a minute; auth, rate-limit and connection changes end it early. The runtime stores no derived quota history. Credit balances remain opaque exact strings, and independent account/model meters are never aggregated.

The runtime holds the built-in Codex and Claude factories and creates both adapters as it starts, in a background warm-up that `createAgentHq` doesn't wait for: it connects to Codex's daemon and brings Claude's history index up to date, one folder at a time, for the allowed roots and the folders the index already holds, at most 128 by latest activity. A CLI that is missing or fails leaves its provider unavailable, as its first request would have; closing the runtime stops the warm-up, and the Claude read process it waits on, at once. Status and database-backed reads do not require a native CLI. Provider IDs flow through contracts, cursors and persistence; core actions, sessions and skills route through the registry. Native protocol parsing and invocation spelling stay with each adapter.

The registry binds callback identity and bounds operations by 30 seconds and the runtime's lifetime; each adapter validates its own native protocol, and neither the registry, the history reads nor the IPC server parses an adapter's output or a response the runtime built again; the IPC client checks a response at its own boundary. Optional capability failures remain separate from session control. A control response the adapter cannot parse quarantines its source, and bounded per-provider lifecycle queues contain overload. Live items stay in the runtime's window, which keeps one entry per item, and never reach the store or those queues, so a turn that streams many items costs no worker call. Admission checks operation support against each provider's fixed support in `src/providers/constants.ts`, without a native call; only the `capabilities` read asks the CLI, for its model catalog and Claude's session skills. A store failure affects shared persistence. Adapters own partial-startup cleanup and native process lifetime; runtime shutdown confirms cleanup before releasing ownership. Version labels are diagnostic metadata, never admission gates. Native input, settings, permissions and authentication remain with the installed harness.

Codex sessions run on Codex's shared app-server daemon, which also hosts terminal sessions. The adapter runs `codex app-server daemon start`, through the host's `codexDaemonLauncher` when it has one, which returns at once when the daemon is running, then connects through `codex app-server proxy`. The daemon's control socket speaks WebSocket and the proxy forwards raw bytes, so the adapter performs the upgrade, masks its frames and bounds each message to the IPC frame limit. The proxy notices a stopped daemon only when it next writes, so the adapter pings every 10 seconds and fails the transport when a ping goes unanswered; the Codex cohort then becomes uncertain and nothing is resent. The next Codex request opens a new connection, so a daemon restart needs no runtime restart. Closing the runtime's connection leaves the daemon, terminal sessions and the runtime's own sessions running, so runtime shutdown leaves their turns, terminals and waiting requests alone, and the next runtime rejoins them. Extra skill roots travel as capability roots of the threads the runtime starts, because the daemon applies `skills/extraRoots/set` to every session.

Sessions another client drives are observed rather than controlled. Codex reports them through the daemon's status broadcasts, filtered to the allowed workspaces, and the runtime reads the daemon's loaded threads each time its connection opens, since a session already running reports no change; Claude reports them through a runtime-owned poll of `claude agents --json`, whose complete list closes every session missing from it; an entry without a process ID, or for a process the runtime started, counts as missing. Observed states live in their own table, which also keeps the workspace, name and creation time the Codex adapter's one read of a session found, or the folder Claude's poll last listed a session in, so `active-sessions` makes no native read. Triggers on that table and on managed thread states append every change to one transition log with a monotonic sequence and the session's folder, so no write path can skip a transition, and each insert prunes a bounded batch of entries older than seven days.

Long-polls wait on the runtime's own changes. After every call, the store worker reports the highest transition sequence with its answer, so a call that recorded a transition, by whatever path, wakes the `session-states` long-polls, which read their page again; the live window reports each change with its window, which wakes the `live-items` long-polls on it. The waits share one primitive with `action-wait`, which the actions module wakes after each receipt change; at most 32 long-polls wait at once, and closing the runtime ends every wait first.

Structured transports own their native processes, with verified POSIX group shutdown. Idle Claude processes close: the session-less read process after 5 minutes unused, and a controlled session's process 60 minutes after its last turn, its settings, agent list and skills catalog kept in memory until input reopens it with `--resume`. That parked state is not persisted. History reads need the read process only until it has once started and initialized, which the warm-up does; the runtime keeps that check, so reading transcripts never starts a `claude` process after it.

Claude connection loss and confirmed controller release are separate facts. The former marks control uncertain; the latter returns an internal proof scoped to the exact controller generation, native identity and workspace. The action owner serializes that proof behind lifecycle evidence and the SQLite lifecycle model releases only its matching uncertain record in the producing runtime. It reuses runtime-shutdown settlement for approvals, submitted actions and paused queues. An admitted close retains its own release/receipt path; stale callbacks and runtime-close races cannot release a replacement owner. A failed proof remains local to that retained Claude controller, while runtime shutdown still requires all owned cleanup to succeed. This per-session transition adds no storage migration, replay or inference, and needs no cache.

Deleting a session belongs to its provider. Codex's daemon owns its rollouts and the index of them it keeps in its own databases, so the adapter asks it with `thread/delete`, never touching Codex's files, and counts a session Codex never saved as deleted. Claude keeps a session as a transcript and the folder beside it in its project directory, which the adapter deletes without following links, before it forgets the transcript in the runtime's index and drops the directory scans in progress, so no scan reads it again. The runtime then deletes its own records in the store worker, in the order their foreign keys allow: the thread and its registration action name each other, so its actions leave the thread before it goes, and go after it. A deletion runs within its request, so its failure reaches the caller.

The runtime preserves native session, parent and fork identities separately from its own managed thread UUID. Confirmed immutable lineage survives restart and enriches native reads that omit those fields; contradictions fail instead of replacing recorded relationships. Lifecycle changes use the same action ledger and uncertainty rules as input.

Native model catalogs and effective settings remain authoritative in each provider. Configuration reads project known fields and bounded native agent/profile metadata, without exposing whole settings documents. Model and effort changes accompany the next explicit input; startup settings accompany create or idle resume. No global configuration files are rewritten. Temporary Claude workspace reads are bounded to four owned native processes. Their cancellation signal closes the transport, and shutdown waits for every starting or ready lane; unconfirmed cleanup cannot release ownership. Native observations are refreshed rather than kept in a parallel configuration cache; the bounded in-memory session metadata retains only startup acknowledgement fields that a later native read cannot return.

File input admission records canonical references and hashes rather than embedding bytes in commands. Dispatch rereads checked descriptors and rejects a changed queue binding before sending native input. Native adapters encode those verified bytes into supported image/document/text inputs. Fixed count and byte limits bound both reads and worst-case native JSON transport. No remote fetching or file-content cache is involved.

Complete final results are separate from the bounded live/history presentation. The adapter validates requested structured output and records exact bounded values with native completion in the action ledger. Selected receipts retrieve them after restart; paged action reads select metadata only. Tool output remains in native history. Output buffers are limited to the current controlled turn, and completion or confirmed control release discards them. Claude output schemas require an idle process restart; Codex applies them per turn.

Native request bodies stay in the controller’s bounded live prompt map. SQLite keeps approval identity, exact turn/runtime correlation, state and reply-action identity; indexed seek queries return durable metadata with optional live presentation. Restart or loss of the native connection expires pending requests. Pipe writes do not establish response consumption, and unanswered delivery uncertainty never triggers a resend.

Session discovery merges native pages rather than copying them. Each folder and provider is a source read a native page at a time, beside the runtime's records of sessions no turn has started, and a session is listed once no source can still hold one before it. Claude's index and the runtime's records read in the list's own order, so a page reads them only past what it lists; Codex sorts by last activity alone and breaks ties its own way, so its reads go one session past a page and past any tie. The cursor keeps, for each source, the latest activity its unlisted sessions can have and the continuation of the native page holding them, so a deep page re-reads at most one native page of a source and doesn't read a source whose sessions can't be next. One provider's native reads run one at a time, since Claude indexes in one worker with at most four directory scans open, and a page's native reads share 25 seconds, which leaves the rest of the IPC client's 35-second wait for the store reads that complete it; a source they don't reach is left out of the page and named.

Bounded session evidence uses the native history boundary and rechecks workspace authorization per read. Exact references bind normalized UTF-8 text to provider, session, turn, item and hash. A partial-page continuation validates its content digest before returning another body fragment. Source pages stay bounded; no transcript body cache is kept. Claude's worker seeks current-chain UUID/kind/offset indexes and rereads only selected records after incremental indexing. Indexing scans each transcript in one reused 64 KiB chunk and decodes each record once; a record that spans chunks is read again whole into one reused buffer, instead of being copied again for every chunk. The statements indexing runs for each record come from the worker's statement cache. A transcript whose identity, size and modification time match an index that reached its end is skipped without a transaction, and each directory scan tracks the transcripts it has seen in memory, so reading unchanged transcripts writes nothing to SQLite. A scan continues across calls, and starts over once the directory's modification time shows a transcript was added or removed since it opened, because a directory iterator may skip entries added after it opened; a scan that completes has seen every transcript the directory held.

Each store worker call indexes at most 8 MiB of new transcript bytes, so one call stays well under a second and other store requests run between calls. A call that stops early answers `indexing` and saves where it stopped; the adapter calls again until the read answers, within its 30-second budget, and a later read continues the same way. The call's first record is read whole even when it is larger than the budget, up to the 32 MiB record limit, so indexing always advances. A call that stops while it holds back a hidden record for the parent that follows it returns, through a SQLite savepoint, to before that record, so the next call indexes the two together and the turn isn't split; only a call that held it from its own start through its whole budget indexes it as its own turn instead. At the transcript's end a held record still starts a turn of its own, since its parent may never be written and returning there would hide the records after it from that read.

The budget comes from a measurement on 2026-11-04, on Linux with an AMD Ryzen 7 5700X and Node.js 24.15.0, timing `ClaudeHistoryModel.read` from the built package in a worker thread with the store worker's 16 MiB young generation, one call per batch:

| Transcript                                            | Indexing rate      |
| ----------------------------------------------------- | ------------------ |
| Short messages, about 840 bytes a record              | 15 to 16.5 MiB/s   |
| Tool calls with 4 KiB results                         | 76 to 80 MiB/s     |
| Real transcripts of 6 to 98 MiB, 546 to 3,963 records | 85 to 186 MiB/s    |
| One 31.5 MiB record                                   | about 150 ms whole |

At the slowest rate one second indexes about 16 MiB, so the budget is half of that. Calls then took at most 0.56 seconds on short messages, 0.11 seconds on tool calls and 0.09 seconds on the real transcripts. To measure again after a change to indexing, build the package, write a transcript of short user and assistant messages of about 32 MiB, then time each `read` of its `items` in a worker thread with `resourceLimits: { maxYoungGenerationSizeMb: 16 }` and count the bytes each call indexed from `agent_hq_claude_file.byte_offset`; keep the budget a power of two near half of what one second indexes.

An item detail's search for a result's call stays within one worker call, because its worst case does too. It reads at most 32 ancestors in the turn and 64 MiB of their records; on the same machine and Node.js version, in the same worker setup, it searched 60 to 62 MiB of plain or escaped text in 0.10 to 0.16 seconds and 38 MiB of records made of many small content blocks in about 0.29 seconds, so about 0.5 seconds at the full 64 MiB.

Input provenance joins exact acknowledged native input identities and text fingerprints with action records. Authenticated host text, including an explicit skill's prepared invocation, additionally matches its browser admission's selected thread and fingerprint. The runtime saves hashes rather than another copy of ordinary input. Native user roles and quoted feedback remain unknown unless that correlation succeeds. Every historical item has an untrusted content boundary and grants no authority.

Claude steer writes use the exact action UUID as the native user UUID. Native `queued_command` prompt records retain their graph UUID for chain, cursor, detail and image addressing, and their validated `source_uuid` for provenance. They inherit the running turn and hash only the original first text block, before attachment labels. A bounded primary-key ledger lookup checks that acknowledged steer against its provider, session, target turn and hash; late ordinary-user replays may present the input UUID as their turn. Other or ambiguous identities stay unknown. Projection version 12 invalidates older replaceable indexes, including 13.1.5 version-11 entries, using the same indexing budget without a schema migration or transcript changes. Published record-before-parent handling is retained. Exact source UUID, hash, turn and body matching reconciles queued history with its live replay.

## Storage

One SQLite worker owns the runtime's persistence, with its young generation capped at 16 MiB. Its connection sets a 16 MiB `journal_size_limit`, so the WAL file shrinks back after a checkpoint instead of keeping its largest size. The complete definition, including provider history indexes, is src/store/schema.sql. Fresh initialization creates the schema and its singleton agent_hq_schema stamp, containing the runtime's schema hash, the action-key fingerprint and the package version that wrote it, in one transaction. Reopening validates that stamp through a read-only connection before opening a writer and rejects a mismatched private key. This preserves rejected database bytes and their WAL instead of triggering SQLite's close-time checkpoint. Application-owned objects are outside this stamp. The runtime leaves user_version with the host. The package reads only its current schema: any other stamp is refused with an error naming the package version that wrote it, and storage is never migrated.

The main thread runs a worker operation with one typed call, `call(model, method, ...args)`, whose types come from the worker's model classes, so each operation is declared once, as a model method. The runtime's own code builds the messages on both sides, so neither thread parses them again; client requests, native CLI output and files on disk are validated where they enter. The worker prepares each statement once and caches it in SQLite's tag store, which holds 256 statements. Observation de-duplication rows in `agent_hq_event` belong to the current runtime: a repeated lifecycle observation is recognized within it, and startup deletes the rows earlier runtimes left. An action records the native step it takes in its `phase` column; the request ID the runtime sends the CLI names the action and phase, and an outcome for a phase the action has left changes nothing. A browser action keeps its state, runtime epoch and native action ID in columns of their own.

All of the runtime's tables, indexes and named constraints use the agent_hq\_ prefix. Hosts own their application prefixes and definitions. They may open a separate connection using the canonical path and connection settings supplied by the Node runtime. Prefixes express ownership within a trusted process; they do not protect against another process with access to the file. Direct application writes to the runtime's tables are unsupported.

Maintenance closes new runtime admission, drains admitted operations and their nested calls, and waits for earlier worker commands. Native evidence needed to finish admitted work continues during the drain. It refuses active native execution. During the host callback, new native event persistence waits for release through the existing bounded event lane; an already accepted scheduled stop also waits. The host callback owns its connection and must not call the runtime, start native work or leave its transaction open. Callback failure releases admission without classifying the host's SQL effect as rolled back.

A host connection and a jg-agent-hq API call cannot share one SQLite transaction. Cross-boundary work needs idempotency and reconciliation owned by the application. SQLite permits one writer at a time; unrelated host connections must cooperate with maintenance. The API reference owns connection settings, signatures and error contracts.

Snapshot capture is ordinary admitted work, so maintenance excludes it while native work continues. It holds the state root's `snapshot` lock, a jg-locks lock in `.runtime/locks` beside the `runtime` lock the runtime holds for its lifetime. The SQLite worker performs a WAL-aware backup through its own connection in bounded steps, interleaved with native evidence; writes from another connection would restart or split it, so hosts keep their own tables quiet. The worker then deletes the Claude history index from that full copy, without foreign key checks or a journal because the copy is discarded, and writes the snapshot database from it with `VACUUM INTO`, which keeps every table's rowids, unlike a plain `VACUUM` of a table without an integer key. The index is most of a busy database and is rebuilt from the transcripts, so snapshots stay small. The database and action.key files and the three-record JSONL manifest are streamed, with an exact final completion marker. No artifact cache is used because each capture/inspection must establish current exact bytes.

Offline verification and restore run in a separate worker. Restore refuses a snapshot from another schema, validates a staged copy before exposing new private state, and invalidates native ownership, live approvals and queued readiness. Source roots and paths remain evidence; the host must select allowed roots anew. Repository files, native histories/authentication, the Claude history index and remote durability remain outside the snapshot; a recovered runtime rebuilds the index from the transcripts on its first Claude history read. See [recovery](recovery.md).
