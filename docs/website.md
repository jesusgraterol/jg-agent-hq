# Public website

`website/` is a private Astro workspace, built independently from the Node runtime. `src/site.config.ts` owns the bounded page catalog, including the worked examples and reads the package version from root `package.json`. The production origin is `https://jg-agent-hq.jesusgraterol.dev`. No browser request fetches native sessions, account usage or npm metadata.

The canonical content loader reads exactly root `README.md` and `api/README.md`, outside the website root, once each per content sync. It accepts regular files up to 1 MiB, rejects raw HTML/unsafe links, and renders each document's own heading. Canonical HTML links resolve to the site; the error registry and recovery guide link to public GitHub source. Markdown counterparts retain their canonical source text. The homepage HTML/Markdown share the narrative in `src/content/home.ts`. Worked examples share narrative records in `src/content/examples.ts` and pure HTML/Markdown models in `src/content/example-documents.ts`; the bounded reader additionally allows only the authoritative `examples/control-session.ts` file. A separate native Astro collection loads this source body during content sync, so relocated server chunks never resolve repository paths. The complete helper is copied verbatim into its HTML and Markdown walkthrough, beside a runnable caller. Expected and illustrative results are labeled explicitly. Navigation, metadata, sitemap and agent discovery describe the same bounded page set. There is no content cache or recursive repository crawl.

The shared `jg-personal-astro-ui@0.5.0` public components, theme/prose CSS, Markdown plugins and syntax theme own reusable controls, navigation, code windows, typography, light/dark palettes and reduced motion. `jg-site` owns structured data and llms.txt generation. The homepage hero follows the other jg sites (`hero-backdrop`, `display-title`, `lede`, two default buttons) beside an architecture map of the app, the controller and the native CLIs. Four capability rows (sessions, prompts, output and usage, local storage) each name their real commands beside an illustrative preview. The usage preview separates Claude's model-scoped meters from Codex's windows, credits and earned resets; the storage preview shows capture while agents work and restore. A grid of six smaller capabilities follows, each with one real command or API name, then local setup. A unit test requires every homepage name in `src/content/home.ts` to appear in `README.md` or `api/README.md`. The header carries the sibling sites' source-repository link. Keep visitor text short: one sentence per capability, with previews doing the explaining. The examples page publishes session control as a three-step flow naming the commands it sends, a short requirement list, result-first tabs and complete copyable source. The homepage's walkthrough links and canonical source links resolve to the implemented walkthrough anchors. There is no standalone Markdown call-to-action. Documentation pages use the shared documentation shell, document-title typography and outline from the rendered headings. The outline is a native disclosure on smaller screens and sits beside the article on desktop. Local setup uses shared steps while retaining its commands and copy controls. Documentation routes remain thin. `/404.html` has no canonical and is excluded from discovery; the deployment check requires an actual HTTP 404 for a missing address.

## Verification

Install the workspace from the root and install its pinned Playwright Chromium. `pnpm check:package` checks only the runtime, including a real tarball consumer. `pnpm --dir website check` checks the site. `pnpm check` composes both. Root build/type/test/format inputs exclude the website; the publishable package's explicit file list excludes all website files and dependencies.

Signed Git integration fixtures create their own disposable author/signing metadata. Git and `ssh-keygen` must be available; the tests do not require your Git identity or SSH agent.

Website `check` selects essential source/content safety, output privacy and exact-release/deployment guards. It builds once, retaining the existing Chromium DOM verifier, then reuses the artifact for essential integration tests. `test:full` and `check:full` add all content, metadata, asset and production-browser cases on explicit local request only. Unit, integration and E2E scripts select separate categories; no tests live under Astro's route directory. Run changed integration files three consecutive times without retries. Browser checks use `jg-playwright` for asset readiness and horizontal overflow, retaining the direct axe scan for its WCAG 2.2 tags. Checks include 320px, tablet and desktop, both system themes, keyboard/focus/menu/theme persistence, clipboard success/failure and external-link notices. Network destination checks do not run during local builds.

Artifact verification uses one Chromium instance with scripts and resource loading disabled, closes it in `finally`, and checks local references/anchors, metadata, canonical Markdown, discovery, image dimensions and forbidden build output. Production browser tests exercise actual scripts and fonts. These checks establish Chromium on the tested host; other browser engines and macOS need their own runtime evidence.

## CI and delivery

The build emits only static files in `website/dist/`. Public destination checks require the exact root version from npm's registry API, plus the expected GitHub/jg-skills/jg-packages content. npm's browser page can reject automated reads and is not a deployment dependency. The deployment verifier then checks canonical pages, Markdown, discovery, image availability and real missing-page behavior at the fixed HTTPS origin.

`.github/workflows/check.yml` temporarily composes one package build, essential native unit/integration selections, existing type/format gates, and `pnpm --dir website check` on pull requests to `main`, pushes to `main` and manual dispatches. Root local commands remain complete until their aliases join the next normal package release; see [testing policy](testing.md). Both Node 24.15.0 (the engine floor) and 24.22.0 (the pinned LTS) must pass. Installs use the frozen workspace lockfile and its existing narrow dependency-build policy, without dependency caches because this workflow publishes packages. Browser installation includes Chromium's runner OS dependencies. The local 2.0.0 qualification additionally uses Node 24.22.1; the configured CI pin remains 24.22.0.

Only the floor-Node job uploads `website/dist` and the consumer-tested npm archive, and only on `main`. A separate job waits for the entire matrix, downloads that exact archive and publishes it with npm provenance through the configured trusted publisher. Only that job receives publishing OIDC permission. Deployment waits for publication, checks the exact npm release/public destinations, then deploys the same Pages artifact without rebuilding. Only the deploy job has Pages write permission and its own Pages OIDC permission. Pull requests have no deployment or production credentials. Superseded pull-request runs can be canceled; an active main publication/deployment is allowed to finish. No release/tag trigger or long-lived npm/provider credential is needed.

The repository's Pages source must be GitHub Actions, with custom domain `jg-agent-hq.jesusgraterol.dev` and working HTTPS DNS/certificate configuration. The `github-pages` environment should permit deployment from `main`. A successful workflow is followed by `verify:deployment`, which checks actual HTTPS content, direct Markdown media types/content, discovery, assets and an actual missing-page 404. A locally passing build does not establish a live deployment.

For Cloudflare-proxied hosting, create a Configuration Rule matching `http.host eq "jg-agent-hq.jesusgraterol.dev"` with Email Obfuscation off. Otherwise Cloudflare interprets the package's `name@version` install argument as an email address and rewrites the verified HTML. Keep this rule restricted to the public hostname; domain configuration belongs to the operator.

## npm release

The package already exists on npm. Its trusted publisher must authorize GitHub user `jesusgraterol`, repository `jg-agent-hq`, workflow `check.yml`, direct `npm publish` and no publishing environment restriction. npm CLI 11.5.1 or later and Node 22.14.0 or later support this flow; the publishing job uses the configured Node 24.22.0 runtime. No local sign-in, npm token or per-release security prompt is required.

The packed-consumer integration test retains its exact tested archive in `JG_HQ_RELEASE_DIRECTORY` when CI supplies that directory. `scripts/release/` validates a bounded registry response and requires a stable version newer than npm's latest release. An existing version is skipped only when its SHA-512 integrity matches the tested archive; a changed artifact under the same version fails. The publish job submits that archive once, waits up to 10 minutes for npm processing and confirms its integrity; when npm takes longer, the job fails saying the release is published and a rerun finishes it. Failed or uncertain submissions stop the job; inspect the registry and run before retrying. Rerunning on `main` safely skips an identical release and continues deployment.

Inspect the actual completed Actions run and HTTPS result. Public contract corrections require a versioned release before private consumers update their exact pins. Website-only changes need no runtime release when packed contents stay unchanged. Registry reads use deadlines and bounded bodies without caching; there are only two version lookups before a new publication and a bounded visibility check afterward.

## Rollback

For a website regression, revert the responsible source change through `development` and a PR to `main`, then let the same checks and release gate produce/deploy its verified artifact. Keep the fixed production origin. Do not substitute an unverified local build or deploy a pull-request artifact. If deployment fails, inspect that run before retrying; a failed gate publishes no replacement site.

npm versions are immutable. A package defect requires a corrected version and another verified publication through `main`, followed by exact consumer-pin updates. Preserve the failing release evidence; do not overwrite a published version or add a compatibility path to conceal it.
