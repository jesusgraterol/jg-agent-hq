# Public API

Import the named exports from `jg-agent-hq`. Internal module paths are private.

Intentional Node API failures use `Exception` from `jg-exception`. The [error reference](../errors/README.md) defines their named string codes and stable messages. `getErrorKind(error)` reads the safe classification a jg-agent-hq error carries in `data.kind`, and returns `operation-failed` for any other error. `PUBLIC_ERROR_CODES` and `PUBLIC_ERROR_MESSAGES` are available from `jg-agent-hq/contracts` for the eight safe client classifications. SQLite-worker responses retain the originating application code; arbitrary worker failures become `JG_AGENT_HQ_STORE_FAILED`. Browser and IPC error bodies expose only their established safe classification and message.

## Lock lifecycle

The runtime takes two [jg-locks](https://jg-packages.jesusgraterol.dev/packages/jg-locks/) locks in the private `.runtime/locks` folder of the state root: `runtime` for the runtime's lifetime and `snapshot` while a capture runs. A lock's owner.json names its process ID, host, nonce, program and start time; the `runtime` lock's nonce is the runtime epoch that clients bind each request to. A live `runtime` holder makes another startup fail with RUNTIME_ALREADY_OWNED, and capture waits up to 120 seconds for a live `snapshot` holder.

A holder whose process is gone is never taken over automatically, because the processes it started may remain. The one exception is a runtime that stopped without releasing the state root, which the host's `isPreviousRuntimeStopped` check proves under [runtime lifecycle](#runtime-lifecycle). Otherwise, check what the holder left, then take its lock over from exactly that owner with jg-locks: `acquireLock(name, { root, recoverFrom: owner })` with the owner `inspectLock(name, { root })` reports, or `jg-locks recover <name> --nonce <nonce>` with `JG_LOCKS_ROOT` set to the locks folder. The locks coordinate cooperating processes and don't isolate hostile code running as the same OS user.

## Shared storage

Trusted Node hosts may pass `initializeHostStorage: IStorageMaintenanceOperation<void>` to `createAgentHq`. Startup awaits this optional callback exactly once after acquiring exclusive runtime ownership and opening the validated SQLite worker, before constructing providers, observing Claude, creating action controllers, admitting IPC or reconnecting native sessions. It receives an independent storage descriptor. A retained Codex turn may keep running in its independent daemon during this phase; the new runtime has no native connection or event writer yet. The host must coordinate its other writers, use its own transaction and close its connection before returning. It must not start native work or call runtime APIs. Callback errors propagate unchanged after startup closes its store and releases ownership; SQL rollback remains the host's responsibility. A failed callback never starts providers or IPC. This option is absent from CLI, IPC and browser contracts. It does not change the live maintenance guard below or migrate native storage.

`hq.storage` returns an independent `IStorageDescriptor` containing the canonical `databasePath`, `schemaHash`, `reservedPrefix` (`agent_hq_`), and required `connectionSettings`: `foreignKeys` true, `busyTimeoutMs` 5000, `journalMode` wal, `synchronous` full, and `journalSizeLimitBytes` 16,777,216. Exported Node types are `IStorageDescriptor` and `IStorageMaintenanceOperation<T>`. No database handle, storage callback, raw SQL command or storage path is exposed by browser contracts or IPC.

`openHostDatabase(storage)` opens a node:sqlite `DatabaseSync` connection to `storage.databasePath` with every setting the descriptor names: foreign keys, the 5,000 ms busy timeout, FULL synchronization and the 16 MiB `journal_size_limit`, which SQLite applies only on the connection whose write starts the WAL over. The host owns the connection and closes it. The connection reads the runtime's tables but can't change them: SQLite refuses with its `not authorized` error a statement that writes rows of a table under the reserved prefix, or creates, alters or drops a table, index, trigger or view under it or on such a table. It fails with JG_AGENT_HQ_STORE_FAILED when the database can't be opened. Keep WAL mode; do not change database-wide settings while the runtime is running. Hosts own their table prefix, definitions, connection lifetime and user_version. The runtime's tables and indexes are reserved. A nonempty database requires the current singleton agent_hq_schema stamp, which records the schema hash, the SHA-256 fingerprint of action.key and the package version that wrote the database. Startup rejects any other schema with JG_AGENT_HQ_STORAGE_INVALID before opening a writer; its message names that package version, or reports another jg-agent-hq version when the stamp records none. Rejected storage remains unchanged. A different valid-length key fails with JG_AGENT_HQ_ACTION_KEY_UNAVAILABLE before a writer opens. Fresh initialization is transactional.

`await hq.withStorageMaintenance(operation)` passes the storage descriptor to the async operation and returns its result. It closes admission before draining accepted runtime operations, allows their awaited nested calls and required native evidence to finish, and checks for active native execution before invoking the callback. Concurrent maintenance, new runtime requests, browser host effects and shutdown conflict while maintenance is held. During the callback, native event persistence waits in its existing bounded lane, and an already accepted scheduled stop waits for release. The callback must not call the runtime, start native work or leave transactions open. Its errors propagate unchanged; it owns rollback and reconciliation for its SQL effects. After success or failure, the runtime's admission resumes. Calls after shutdown use JG_AGENT_HQ_RUNTIME_NOT_RUNNING.

The host must coordinate every application connection that can write during maintenance. A shared file gives SQLite transaction isolation, not an atomic transaction spanning host SQL and jg-agent-hq API calls. The runtime does not expose its worker connection. Snapshot scheduling and remote backup operations belong to the host application.

## Snapshot and restore

Capture a running runtime with its `hq.createSnapshot(destination)` method, and import restoreHqSnapshot, packHqSnapshot and unpackHqSnapshot from jg-agent-hq in a trusted Node host. They are absent from browser contracts and IPC. The exported types are IHqSnapshotInspection, IHqRestoreOptions and IHqRestoreResult.

| Operation                                               | Contract                                                                                                                                                                                                                        |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hq.createSnapshot(destination)`                        | Capture the running runtime while its agents keep working into an absent absolute destination under an existing canonical parent. Host connections must not write host tables until it resolves. Returns IHqSnapshotInspection. |
| `packHqSnapshot(snapshotDirectory, archivePath, key)`   | Inspect the snapshot, then encrypt it into one new private file at an absent absolute path under an existing canonical parent. Returns the snapshot's IHqSnapshotInspection.                                                    |
| `unpackHqSnapshot(archivePath, destination, key)`       | Decrypt and verify an archive, then write it into an absent snapshot directory and inspect it. Returns IHqSnapshotInspection.                                                                                                   |
| `restoreHqSnapshot({ snapshotDirectory, destination })` | Validate before creating an absent recovery destination, copy and validate staged files, then expose the recovered state directory. Returns IHqRestoreResult. All proposed destination connections must be stopped.             |

Capture runs as admitted runtime work, so host maintenance excludes it, and holds the state root's `snapshot` lock throughout, waiting up to 120 seconds for another live holder. Native turns, ownership changes and evidence keep flowing: the store worker backs up the database through its own connection in bounded steps, then compacts that copy in one short step that holds the worker. Host connections must not write host tables for the complete capture, because a write from another connection restarts or splits SQLite's backup. Attached databases and external files are outside this coherence contract.

SQLite's worker-owned backup API includes committed WAL data and every table in the main database, including application tables. The snapshot leaves out the rows of the Claude history index, `agent_hq_claude_file` and `agent_hq_claude_entry`, which make up most of a database that has read Claude sessions: the worker deletes them from a full copy beside the destination, writes the snapshot database from that copy with `VACUUM INTO`, which keeps every table's rowids, syncs it and removes the full copy. The resulting database needs no WAL sidecar. The snapshot also contains the private 32-byte action.key. Capture binds the original canonical state root and checks the key against its startup hash, rejecting a key replaced while the runtime is open. File copy and SHA-256 use 65,536-byte buffers. There is no repository scan, transcript copy or artifact cache, and no workspace file is captured.

manifest.jsonl holds exactly three records: header, database and action-key. The header records the schema hash, the package version that captured it, the source state root and the allowed roots. A final complete.json binds the complete manifest hash and record count. Directories are private (0700), files are private (0600), and destinations are created exclusively. Runtime sockets, locks, process IDs and provider authentication are excluded.

Every operation inspects the snapshot it reads or writes. Inspection reads the header's schema hash and package version before its shape, then verifies each listed regular file, rejects links, unsafe paths and any further record, and checks the current schema stamp and database/key pairing and SQLite integrity/foreign keys. A snapshot whose header or database comes from another schema is refused with STORAGE_INVALID, naming the package version that wrote it, before any restore output is reserved. Full database verification runs in a dedicated worker. Inspection returns the directory, manifest hash and header. Hashes detect corruption and bind content; they do not authenticate a snapshot supplied by an untrusted party.

Restore leaves every existing destination untouched, including an empty directory, repository or live state root. Use a new directory. It validates the source before reserving that directory and validates the staged copy independently against the initially inspected manifest hash before changing recovered state. On success, stateRoot points to destination/state, recovery.jsonl retains the source manifest and recovered.json records completion. Caught failures remove only the operation's newly created output. A crash can leave incomplete output; do not open it as a recovered runtime.

Restored live approvals expire and queued input loses readiness. Submitted actions retain uncertainty. Managed native identities become uncertain and require explicit ownership reconciliation. IDs and historical receipts remain intact. No native operation runs during restore.

Call createAgentHq with the returned stateRoot and an explicitly selected allowedRoots array. Runtime construction never imports source root permissions from the snapshot and always assigns a new epoch. Native source workspace paths remain evidence and are not rewritten. Recover repository and native files separately; restore never overwrites a source repository. The recovered runtime rebuilds the Claude history index from the native transcripts on its first Claude history read, as a fresh state root does, so a Claude session is listed again once its transcript is on the machine. Make explicit native ownership decisions before resuming work. Source paths outside the newly selected roots remain unavailable.

These exports use SNAPSHOT_INVALID for incomplete, corrupt, unsafe or occupied snapshot, archive or recovery selections, for a key that is not 32 bytes and for an archive that fails authentication, and SNAPSHOT_FAILED for operational copy, backup, lock, worker or cleanup failures, including a `snapshot` lock whose holder is gone. Capture additionally exposes ACTION_CONFLICT while host maintenance runs or when the `snapshot` lock wait expires. Restore, packing and unpacking expose STORAGE_INVALID for a snapshot from another schema. Operational messages retain private diagnostic causes; no snapshot exception is exposed through public RPC.

An archive is a fixed format identifier, a fresh 12-byte IV, the AES-256-GCM ciphertext of every snapshot file in manifest order, each behind its path and length, and the 16-byte authentication tag. The key is a 32-byte Buffer the host supplies and keeps; the runtime never stores it. Unpacking decrypts the whole archive into a private temporary file beside the destination and verifies the tag before trusting any byte or creating the destination, so a wrong key, a modified byte or a truncation is refused with SNAPSHOT_INVALID and writes nothing. It then writes only the manifest's listed paths at exactly their listed sizes, refuses unlisted, repeated or missing entries, and inspects the result; any failure removes the destination and the temporary file. Packing removes a partial archive on failure. Both stream in 65,536-byte chunks.

Snapshot directories are plaintext local state; archives are the encrypted form for off-machine copies. The host owns the key and its recovery, scheduling, uploads, retention and last-success status. A disk failure can lose every change after the last successful off-machine backup. A local snapshot alone provides no remote durability. See the [recovery workflow](../docs/recovery.md).

Native snapshot qualification on 2026-10-23 used Codex 0.164.0 (gpt-6.1-sol) and Claude Code 2.1.309 (claude-opus-5-5) with controlled native sessions. Quiescent capture, offline restore and explicit root selection changed the runtime epoch and left both providers idle on the recovered runtime. Claude read-tool permissions received exact explicit replies. These observations do not establish a native version admission rule.

## Runtime lifecycle

`createAgentHq({ stateRoot, allowedRoots })` starts one controller and returns `IAgentHq`: its canonical `stateRoot`, its `runtimeEpoch`, which `status` also reports and every action envelope names, a `closed` lifetime promise, `request(command)`, idempotent `close()`, a trusted Node-only `storage` descriptor, `withStorageMaintenance(callback)` and `createSnapshot(destination)`. `request` resolves to the response of its command's kind, typed as `IHqResponseOf<kind>` from `jg-agent-hq/contracts`, so `request({ kind: 'threads', ... })` resolves to `{ kind: 'threads', result: IThreadsPage }` without a cast. Paths must be absolute. Allowed roots must exist and are canonicalized at startup. A client-selected workspace must resolve inside an allowed root. State is a real directory owned by the current OS user with no group/other access. The controller creates it privately when absent.

After optional `initializeHostStorage` completes, the runtime connects both native CLIs in the background, without waiting for their readiness or failing startup when they are unavailable: it connects to Codex's daemon, which also starts observing the sessions Codex runs, and brings Claude's history index up to date for the allowed roots and the folders the index already holds, at most 128 of them by latest activity, one folder at a time. A CLI that is missing or fails reports `unavailable` in `status`, as its first request would have made it; `status` reports a CLI that is still starting `idle`. Indexing waits while host maintenance holds the store, and closing the runtime stops the warm-up, including a CLI start that never answers.

The controller holds the state root's `runtime` lock for its lifetime, as [lock lifecycle](#lock-lifecycle) describes. A live, dead, incomplete or unverifiable existing holder prevents another controller from starting, apart from a dead holder the host's `isPreviousRuntimeStopped` check proves stopped. Before deliberate recovery, establish that the inspected host, its worker and native process group have stopped. Runtime shutdown sends interruption requests across the bounded Claude session cohort concurrently, then closes IPC connections, SQLite and owned native processes before releasing the `runtime` lock. Failed cleanup keeps the lock held. A new runtime receives a new epoch.

Codex sessions outlive the runtime, because they run in Codex's shared app-server daemon. Shutdown leaves them running: it doesn't interrupt their turns, clean their background terminals or answer a request still waiting on one, and their managed records stay bound to the stopped runtime. At startup, the next runtime rejoins each one that had no action in flight, one at a time in the background. It reads the session's state and latest turn from the daemon, binds the record to its own epoch, then joins with `thread/resume` without settings. A turn still running stays the session's active turn. A turn that finished meanwhile completes its action's receipt, without a `result`, and lets a queued entry waiting on it advance. The daemon sends a still-waiting request again on joining, and it opens as a new approval in the new epoch. A session whose latest turn isn't the one the runtime recorded, because another client ran one, or that can't be read or joined, has its ownership marked uncertain for explicit recovery. A crash leaves the same bound records, so those sessions are rejoined too. A restored snapshot marks every session uncertain, so it never rejoins one. Claude sessions are processes the runtime owns: their turns stop with it, and they wait inactive for an explicit resume.

One Codex connection carries every managed Codex session, so a message the runtime can't validate never fails it. A notification about items, text deltas, token usage or a session's status that fails validation is dropped, and a session the runtime controls reports a gap in its live window; a status newer than the runtime knows makes the session `unknown`. A message over 33,554,432 bytes, including its continuation fragments, is skipped through its final fragment without being buffered; a request whose response was skipped fails at its 30-second deadline. A turn start, turn end or approval resolution that fails validation, or a skipped message, whose session can't be known so every session the runtime controls is affected, is made up for by reading the session from the daemon, one session at a time and outside the order other sessions' events keep:

- a turn the saved history shows finished completes its receipt, without a `result`, and lets queued input waiting on it advance;
- a running turn whose start was lost continues, and after a skipped message it continues watched: when Codex next reports the session neither running nor waiting while that turn is still recorded as active, the session is read as if the turn's end had been lost;
- a running turn whose end was lost, or a turn still in progress in the saved history while the session is idle, is read once more 2 seconds later, then completes or makes the session uncertain;
- an idle session whose latest turn is the one the runtime recorded, or that has no turns, is left alone;
- anything else, such as a newer turn, a failed read or a lost approval resolution, marks the session uncertain: its submitted deliveries become uncertain and its pending approvals expire.

A session with an action in flight when a message is skipped, or when its turn start is lost, isn't read, since its newest turn may not be recorded yet; it is watched instead. When a turn's end is both read back and received as its own notification, in either order, the first recorded stands, and the other only fills in a result the first lacked. A session status newer than the runtime knows reads as `nativeState: 'unknown'` in lists and reads. A response to the runtime's own request that fails validation, a message that is neither a request, a notification nor a response, and other invalid framing still fail the connection.

`requestAgentHq(stateRoot, command, signal?)` is a one-command IPC client, typed by its command's kind like `request`. It reads the `runtime` lock's owner and verifies the private socket, binds the command to the runtime epoch and checks the matching response. Cancellation closes that client's socket and reports transport failure; it never undoes an admitted action. Closing a client does not close the host. `stop` accepts a shutdown request; the SDK caller must await `runtime.closed` when it owns the runtime. The CLI confirms the `runtime` lock's release before reporting `state: stopped`.

The socket accepts at most 32 simultaneous connections. Requests are bounded to 65,536 UTF-8 bytes; native and IPC response frames to 33,554,432 bytes. The runtime sends a Codex message over 1,048,576 bytes as fragments of at most that size. Structured transports reject malformed UTF-8/JSON, oversized frames and incomplete tails. Each native connection has at most 32 pending calls with a 30-second response deadline. IPC connections have a 35-second deadline. The SQLite worker bounds its queue to 128 commands, accommodating client reads, native lifecycle observations and action dispatch; collection operations remain limited to one page. Database work runs off the host event loop. The state directory is a same-user trust boundary, not a sandbox against other code running as that user.

After a live Codex connection loss, the runtime rechecks the bounded cohort it controlled with no action in flight before that loss. It stops the old proxy before replacing it, then reads and rejoins each eligible session once, without settings or input. The saved native turn must still match before and after joining. Matching running turns continue; confirmed completions settle their receipts without a result and release their ready queued input. Newer external turns, failed reads/joins and unacknowledged operations remain uncertain. Live output reports a gap, and partial result capture is discarded. This recovery does not claim that native commands or their process handles survived a daemon restart. It never resumes an external session or repeats an uncertain action. A second loss is a new bounded recovery attempt, not a retry of input.

Shutdown preserves a quarantined Codex record's uncertain ownership, producing runtime epoch and recorded native-turn evidence. The next runtime leaves it quarantined for explicit recovery, including when the native turn is still active. Stopping HQ does not prove that Codex stopped or that an uncertain action failed, and never converts that record into a managed inactive control.

Codex approval identities are scoped to their native connection, because a replacement daemon may reuse request IDs. A reissued request opens a new approval; earlier approvals stay expired. A response prepared for an earlier connection cannot write to or decline a request on its replacement. The native response still uses the exact request ID supplied by Codex.

## Providers and capabilities

jg-agent-hq has two built-in providers, `codex` and `claude`. The runtime creates both adapters as it starts, as [runtime lifecycle](#runtime-lifecycle) describes, and bounds every adapter operation by 30 seconds and the runtime's lifetime. Each adapter owns its native protocol validation, processes, authentication, capabilities, history, skill invocation spelling and concrete session controls; the runtime doesn't parse an adapter's output again. Adapters clean up partial initialization before failing, and closing an adapter confirms that the resources it owns stopped. The runtime retains ownership evidence when cleanup cannot be confirmed. Failed construction is not automatically replayed.

An adapter reports normalized observations, items, deltas, prompts, outcomes, observed session states and connection loss. Each outcome echoes the request identity the runtime issued, from which the runtime derives the action it settles, and the runtime verifies the exact receipt, runtime, provider, native session and workspace. A late create/resume outcome also supplies verified native session metadata. Unknown control states cannot establish success or idle ownership. Native permission requests keep their exact reply channel and validation. The runtime answers requests only on sessions it controls: on one of those, a request the adapter can't present is denied rather than approved, while a request on a session another client drives, presentable or not, gets no reply and leaves no record, so that client answers it. A lost turn start, turn end, approval resolution or unidentified notification makes the runtime read the session again, or every session it controls through that provider when the session can't be known; a latest turn whose saved state is still in progress takes its state from the session's status.

`{ kind: 'capabilities', provider, threadId? }` returns `IProviderCapabilities`. The optional managed thread must belong to that provider and an allowed workspace. The response includes provider/session scope, observation time, concrete operation support, and supported input/configuration schemas. Each operation is `supported`, `unsupported`, `unavailable` or `unknown`, with a structured reason when support cannot be established. Supported settings describe whether a change is live or requires an idle restart. Configuration schemas describe typed session and turn settings, their live or idle-restart change mode, and native permission/sandbox choices. Model and effort values come from the native model catalog. Capabilities are observations, not permission grants or execution authority. Operation support is fixed per provider, so action admission checks it without asking the native CLI; only the `capabilities` read asks for the model catalog and, with a Claude `threadId`, that session's skills.

Availability depends on the selected native connection and, for session metadata, that session's initialization. Native settings, hooks, plugins and authentication remain with the harness. Public-API integration tests exercise both native boundaries through the runtime's real persistence and IPC, including compatible version labels and missing-provider isolation.

Local qualification on 2026-10-23 used Codex 0.163.0 and Claude Code 2.1.309 with native settings and authentication in a disposable workspace. Both created and named sessions with selected models and startup instructions, acknowledged a text message, reported native completion and exposed live presentation. Both resumed the same native identity after runtime restart and applied next-turn model/effort selections with native readback. Both also accepted a PNG and UTF-8 document through the runtime's file-reference path and returned a validated structured READY result with per-turn token observations (Codex gpt-6.1-sol; Claude claude-haiku-4-5-20251001). Owned controllers and runtimes shut down cleanly. This checks those controls on this host; other controls and platforms require their own qualification.

An adapter failure that isn't one of the adapters' own exceptions uses JG_AGENT_HQ_PROVIDER_FAILED, retaining safe diagnostic causes. Canonical request/access/state errors and JG_AGENT_HQ_CAPABILITY_UNAVAILABLE retain their meaning. An explicit native rejection may carry `nativeRejection: true`; use it only when native rejection is proven. Timeouts and lost responses remain uncertain and are not retried with a new identity. Capability reads normally return availability data; an unusable descriptor does not disable unrelated session controls. Quota reads return an unavailable observation when no trustworthy measurement can be obtained. A control response the adapter cannot parse quarantines the affected provider. Lifecycle queues are bounded per provider; overflow marks that provider uncertain and stops it while the other provider remains usable. Live items stay in the runtime's memory and never enter these queues. SQLite failures still affect the shared store.

## Read commands

Import `HqRequestSchema`, `HqResponseSchema` and their inferred types from `jg-agent-hq/contracts`. Requests are closed contracts. Responses tolerate additive fields. Provider fields use `ProviderIdSchema`: `codex` or `claude`. Status returns a `providers` array of `{ provider, state, version }`, where state is `idle` while a CLI is still starting, or closed, `ready` or `unavailable`. Reading status starts no provider. The diagnostic version/user-agent string may be null and never decides compatibility.

| Command            | Required fields                                          | Result                                                                                                             |
| ------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `status`           | None                                                     | Runtime epoch, host PID, start time, worker availability and native transport availability                         |
| `capabilities`     | `provider`; optional managed `threadId`                  | Provider/session-scoped support, input/configuration schemas and unavailable reasons                               |
| `models`           | `provider`                                               | Paged native model identities, effort choices, fast support and defaults when observed                             |
| `configuration`    | `provider`, `workspaceRoot`; optional managed `threadId` | Known effective native settings and paged agent/profile choices                                                    |
| `skills`           | `provider`, `workspaceRoot`; optional managed `threadId` | The paged native skill catalog of the session, or of the folder; see [Native skill catalog](#native-skill-catalog) |
| `stop`             | None                                                     | Accepted shutdown and runtime epoch                                                                                |
| `threads`          | `workspaceRoots`                                         | Sessions across folders and providers, last activity first; see [session discovery](#session-discovery)            |
| `thread`           | `provider`, `workspaceRoot`, `nativeId`                  | One native thread's metadata, or the runtime's record of it when its history can't be read                         |
| `items`            | Same target fields                                       | Newest-first persisted native items; optional `turnId`, `textLimit` and `nativeItemId`                             |
| `item-detail`      | Same target fields, `turnId`, `nativeItemId`             | One item with its command, tool call, file diffs and images, or null                                               |
| `item-image`       | Same target fields, `turnId`, `nativeItemId`, `index`    | One image of an item as `{ mediaType, data }`, its bytes in base64                                                 |
| `session-evidence` | Same target fields                                       | Newest-first bounded evidence, exact references and full normalized text continuation                              |
| `usage`            | `provider`                                               | Actual subscription observations                                                                                   |
| `locks`            | None                                                     | The machine's jg-locks locks and their holders; see [machine locks](#machine-locks)                                |

Paged commands accept `limit` (default 32, maximum 128) and an opaque `cursor`. Continue with exactly the same command, target, filters and limit. The cursor binds those fields to the provider continuation. Codex items read descending, and Claude items by native chain position descending. Workspace authorization is rechecked for each request, independently of cursor validation, before selected-thread items are fetched.

`thread` answers for a session whose history its provider can't read, such as a Claude transcript with unsupported records, a missing transcript or a Codex read that fails, with its summary and `historyState: 'unavailable'`: from the indexed transcript when it ran in the workspace, or else from the runtime's managed record of the session, or else from its entry in `active-sessions`, in the same workspace. Only when the runtime knows no such session does the read fail as its provider did. Authorization and request failures stay errors. Adopting or resuming a Claude session whose transcript has unsupported records conflicts with JG_AGENT_HQ_ACTION_CONFLICT.

### Session discovery

`{ kind: 'threads', workspaceRoots, providers?, search?, excludeContinued?, limit?, cursor? }` lists sessions across folders and providers. `workspaceRoots` holds 1 to 64 distinct folders, each authorized like any target, and two that resolve to one folder are refused with JG_AGENT_HQ_REQUEST_INVALID. `providers` defaults to both. A page holds `limit` sessions, 32 by default and at most 128, as `{ data, nextCursor, unavailable }`.

Each folder's native sessions are listed with the managed sessions the runtime created there that no turn has started: each was created empty with `thread-create`, has a native ID and no active or last turn, and isn't closed. Such a session's activity time is its managed record's last update, and its native ID the one the provider gave it at creation, until its first turn writes native history. Its summary comes from its managed record; `thread` answers for it from that record and `items` with an empty page, so its session opens before the provider writes history. Native sessions carry their recorded live state and, when the runtime manages them, their managed name, ownership and ID.

Sessions are ordered by last activity, `updatedAt`, then provider, then native ID, each descending, IDs by code point: Codex before Claude at the same time. Claude's activity is the later of a transcript's modification time and its newest record. `search` keeps the sessions whose name contains it: Claude and the runtime's records compare it ignoring ASCII case, and Codex applies its own `searchTerm`, to the native name even of a managed session. `excludeContinued: true` leaves out the sessions whose `continuedIn` names another session. Both apply before a page is counted, so a page is short only at the end of the list.

`nextCursor` is null once no listed folder and provider has a session left, so a page that ends exactly at the last session has no next one. Continue with the same `workspaceRoots`, `providers`, `search` and `excludeContinued`, in any order; `limit` may change. The cursor carries the last session listed and, for each folder and provider, the latest activity its unlisted sessions can have and the native continuation of the earliest native page holding them, so a page re-reads at most one native page of each source and reads a source only while its sessions can be next. Claude's continuation reads its index without another directory scan unless it starts a source from its first page, as in Claude history below. A cursor used with other filters, tampered with or malformed fails with JG_AGENT_HQ_CURSOR_INVALID. The runtime checks a cursor's encoding, shape and filters, while each provider validates its own continuation inside it. With continuations of the lengths the providers write, a cursor for 64 folders and both providers stays near 12,600 of its 16,384 characters; one that can't fit fails the page with JG_AGENT_HQ_PROVIDER_FAILED.

Across pages, each session that exists throughout and keeps its activity time is listed exactly once. A session whose activity moves past the last listed one, or that appears there, shows on a new first page instead; one that appears after it is listed, unless it ties that session's activity time exactly, where a native list's own tie order decides; one removed before its page isn't listed, except that Claude's index lists a removed transcript until a page scans its folder again. A session the runtime created can appear in a native list while its first turn starts; a page lists it once.

A provider that can't be read for a folder, because it isn't installed or fails, or that the page's shared 25-second budget for native reads doesn't reach, such as Claude history still being indexed, is left out of the page and named in `unavailable` as `{ provider, workspaceRoot }`. Its sessions stay out of the pages that continue the list; a new first page reads it again. Native reads of one provider run one at a time, and Claude's indexing continues across reads as described in Claude history. The other errors fail the read: JG_AGENT_HQ_TARGET_FORBIDDEN for a folder outside the allowed workspaces, JG_AGENT_HQ_REQUEST_INVALID, JG_AGENT_HQ_CURSOR_INVALID and JG_AGENT_HQ_STORE_FAILED.

`items` reads newest first, its only order, and its cursor continues toward older items. `textLimit`, from 1 to 65,536 and 65,536 by default, cuts each item's `text` to that many UTF-16 code units on a code-point boundary and marks it `isTruncated`. `nativeItemId` with its `turnId`, and without a cursor, returns that item alone, cut at `textLimit` like any page; a hidden item, an unknown one, or one outside that turn returns an empty page. Codex has no lookup of one item, so it reads that turn's items, 128 at a time, until it finds the item.

`item-detail` returns `IItemDetail` for one item of a turn, or null for a hidden or unknown item, or one outside that turn. `item` is the item as an `items` read of it returns it. `command` is `{ command, output, isOutputStartCut, exitCode, durationMs }` or null: a Codex `commandExecution` gives every field, a Claude `Bash` call its command, its result the command and its output, from the result's stdout and stderr or else its text, and a `!` shell input or output the same; Claude records no exit code or duration. `tool` is `{ server, name, input, result, isResultStartCut }` or null, with `input` and `result` as text: JSON for Codex `mcpToolCall` and `dynamicToolCall`, and for a Claude call its input as JSON and for its result the text of its content, an MCP tool's name split into its server and tool. A Claude result takes its command or tool name from the call it answers, which the runtime looks for among its 32 nearest ancestors in its turn. `files` lists each changed file with `path`, `added`, `removed` and its unified `diff`, from Codex `fileChange` and Claude Edit and Write results; a created or deleted file without hunks is its whole content, every line added or removed. `images` lists every image the item holds or names, at most 64, in order: `{ index, mediaType, byteCount }`, where `mediaType` is `image/png`, `image/jpeg`, `image/gif` or `image/webp` when its first bytes are one of them, and both are null for an image the item only names, such as a Codex `imageView` or `localImage` path or a URL. Output and results longer than 65,536 UTF-16 code units keep their last 65,536, on a code-point boundary, with `isOutputStartCut` or `isResultStartCut` set.

`item-image` returns the image at `index`, from 0 to 63, in the item's `images`, as `{ mediaType, data }` with its bytes in base64. A Claude image comes from an `image` block with a `base64` source, in the record's message or in a tool result's content. A Codex image comes from an `imageView` item's path, a user message's `localImage` path, or an `image` part's base64 `data:` URL; no other URL is fetched. A path must be absolute. Its file is opened without following it when it is itself a symbolic link, and without waiting on a pipe, and it is read only when it is a regular file; directories in the path are resolved as usual. An image is returned only when its first bytes are PNG, JPEG, GIF or WebP, which set `mediaType`, and it is at most 4 MiB, so its base64 fits in one IPC response. Anything else, including a hidden or unknown item, one outside that turn, or an index past its images, fails with the `image-unavailable` kind.

Threads expose native state, the live session `state` described under [session states](#session-states), `historyState` (`available` or `unavailable`), ownership (`external`, `managed` or `uncertain`) and nullable `managedId`. A managed thread uses its managed name; an external thread retains its nullable native name. Timestamps use Unix milliseconds. Discovery projections are not authoritative transcript history and never cache a conversation body. Repeated Codex history reads go to its native APIs so a completed turn whose items have not flushed can be read again later. There is no resume-to-read behavior or Codex transcript-file parser.

## Bounded session evidence

`session-evidence` enforces a 65,536-byte total serialized response budget, including the IPC envelope. It accepts `limit` (default 32, maximum 128) and an opaque `cursor`. A request inspects at most eight source items, so it may return fewer than its limit. Continue until `nextCursor` is null, including when a filtered page is empty.

`session-evidence` selects `provider`, `workspaceRoot`, `nativeId`, and optional `turnId`, `nativeItemId` and `kinds` (the history item kinds, matching the kinds `items` presents). Items arrive newest first. Each fragment has `reference: { provider, nativeId, turnId, itemId, sha256 }`, `text`, `offsetBytes`, `totalBytes`, `isComplete`, `contentState`, native type, kind and provenance. The hash identifies the complete normalized UTF-8 text, not the fragment or raw transcript record. Non-text native blocks retain explicit labels; this API does not return raw provider payloads or binary attachments. `isComplete` is true only on the final fragment of supported, untruncated normalized text. `contentState` distinguishes available content, unsupported native content and a provider preview. Concatenate fragments for one exact reference in byte-offset order and verify its total length and hash. Empty native history returns an empty terminal page; missing or unverifiable history reports its provider's unavailable error.

Text chunks contain at most 32,768 UTF-8 bytes and shrink when escaping or metadata consumes the response budget. Cursors bind all query fields and the content of a partially consumed native page. Changed content, changed query scope or a changed Claude chain revision uses CURSOR_INVALID; start a fresh read rather than joining different evidence. New native pages use the provider's continuation, not an immutable transcript snapshot. Newly arriving or removed history may therefore require a fresh evidence read. Authorization is rechecked on every request before content access, and no alternate raw-file path bypasses a denial.

`HistoryItemSchema` and evidence fragments expose `provenance: { origin, source, nativeInputId, nativeInputSha256, actionId, contentBoundary: 'untrusted', grantsAuthority: false }`. Origins are operator, agent, tool, system or unknown. Native assistant/tool kinds establish only their observed category. A native user role, quoted operator text or an imported message cannot establish an operator. The runtime correlates a submitted input only when its exact native message/client identity, thread/turn and `nativeInputSha256` match the acknowledged action ledger. A provider's user message carries `nativeInputSha256`, the SHA-256 of the text its native input sent: a Codex message's first text part, or a Claude record's string content or first text block, with a slash command or skill, which Claude records as command markup, read back as the `/name args` it sent. It is hashed before the parts the same input added after the text, such as a skill or attached files, and before a page cuts the text, so those messages correlate too. Programmatic host submissions have source `host-action` and unknown actor. An authenticated browser submission additionally requires the same selected thread and text fingerprint, yielding `authenticated-host-action` and operator provenance. An explicit skill's fingerprint is its prepared invocation, the `$name args` or `/name args` the session received, which the browser submission takes once its action is admitted. A message without a native input identity, or whose sent text differs from the action's, stays unknown. Saved history and live windows apply the same ledger verification. A verified authenticated browser input additionally carries optional `browserActionId`, the original browser intent UUID, so clients can reconcile a local pending row before its POST response arrives. Unverified inputs never carry this field. A native acknowledgement that changes retained live provenance advances the window revision and wakes conditional live reads. Provenance remains historical evidence and grants no current approval, execution authority or tool permission; quotations remain inside its untrusted content boundary.

Codex uses its native descending item API with unloaded thread metadata. It never reads Codex transcript files. Claude uses indexed current-chain byte locations, exact UUID lookups and separate bounded seeks per selected kind. Its cold index uses 8 MiB batches and a 30-second operation budget; selected evidence reads parse at most 4 MiB of records beyond the first. Continuation revalidates and rereads one bounded native page to detect content changes rather than caching transcript bodies. Work and memory per read are bounded independently of history growth; reconstructing a large body may reread that source page. No conversation-body cache is maintained.

## Native configuration

`models` returns native model IDs, display metadata, nullable effort choices/defaults, a nullable `supportsFast` and bounded continuation. Codex reports fast support when a model lists the `priority` service tier, and Claude when the model's `supportsFastMode` is true; null means the catalog doesn't say. Model/effort names are not fixed to a CLI release. Codex retains its native cursor; Claude uses an inventory revision and stable model key. Changed catalogs invalidate continuation.

`configuration` accepts `provider`, authorized `workspaceRoot`, optional managed `threadId`, `limit` and `cursor`. Session selection must match both provider and workspace. The result includes `nativeId`, `workingDirectory`, known `effective` settings, bounded `instructionSources` with `isComplete`, and one page of native `choices` (`agent` or `profile`). Null means unknown or unavailable, never a fabricated default. A null `choices` value means the optional native inventory is unavailable; an empty array means a known empty inventory. Effective settings remain readable when Claude omits its optional agent catalog. Native inventory is bounded to 4096 entries; choice continuation binds the query and inventory revision. Instruction source paths are metadata only; the runtime does not load those files through this operation. Claude uses an owned session's settings or a disposable workspace-scoped read process with no user prompt. Claude records a conversation's instructions once (`--system-prompt-snapshot`, on by default) and reuses them on resume, so `systemInstructions` and `developerInstructions` are reported only for a session whose current process started its conversation, and are null for one that resumed it. `effective.fast` is whether the session uses fast mode. Codex reads it from the service tier its start, resume and later `thread/settings/updated` report. Claude reads it from the `fast_mode_state` of its latest start or turn result, counting `cooldown` after a rate limit as on, and before any from its settings read. `effective.fastUnavailableReason` is Claude's `fast_mode_disabled_reason`, such as `extra_usage_disabled`, while fast mode can't serve the session, and null otherwise. It leaves out `sdk_opt_in_required`, which Claude reports while fast mode is simply off, since turning it on is that opt-in. At most four workspace read processes run concurrently; cancellation and runtime shutdown confirm their exit, including reads still initializing. Unconfirmed cleanup retains runtime ownership. Whole configuration documents, source layers and credentials are not returned.

`thread-create`, `thread-resume` and `thread-adopt`, for the resume it runs, accept optional `settings`: `model`, `effort`, `fast`, `outputSchema`, `permissionMode`, `systemInstructions`, `developerInstructions`, plus Codex `sandbox` or Claude `nativeAgent`. The workspace is the native working directory. Codex system/developer instructions map to native base/developer overrides. Claude system instructions use `--system-prompt`, and developer instructions use `--append-system-prompt`. Omitted fields keep native defaults. These are explicit native settings, separate from native tool approvals. The action envelope byte limit still applies.

Startup settings require an idle restart, using close followed by explicit resume; they cannot be attached to active input. Codex may retain a loaded idle thread after unsubscribe and ignores resume overrides there. The runtime rejects startup overrides on such a thread; restart the runtime's native connection before applying them. It never acknowledges an ignored model change. Claude opens a new native process for explicit resume, preserving the exact native session ID. Native profile selection and Codex native agent selection are not exposed as startup overrides; discovery does not imply a supported setting change.

A `message` or `queue` accepts optional `settings: { model?, effort?, fast?, outputSchema? }`, applied at delivery. `fast` selects the provider's fast mode, and `false` turns it off. Codex sends it as the `priority` service tier, or `default` for off, on `thread/start`, `thread/resume` and `turn/start`, where it also applies to later turns. Claude sends `fastMode` through `--settings` at startup and through a flag-layer update before input, and a parked session reopens with it; this flag setting is also the opt-in Claude requires before fast mode serves an SDK client. Fast mode can cost more usage, and Claude offers it only on some models and plans. Codex accepts an output schema per turn; Claude requires it to match the process schema, except that the runtime can install its shared directed-request envelope through an idle restart of the same native session. Codex uses native turn parameters; Claude acknowledges a native flag-layer update before sending that input. Startup instructions, permission settings and agent selection are excluded from this live path. Queue entries retain explicit settings; omitted options inherit native settings at delivery. Native rejection, partial control failure or lost acknowledgement never causes automatic input replay. Ordinary settings are not written to native configuration files. Confirmed startup instruction selections stay in the owned controller's memory; settings unavailable from native observation after reconnect are null.

Managed threads expose `nativeLineage: { sessionId, parentThreadId, forkedFromId } | null`. Native IDs are kept exactly as observed; a session ID can differ from the thread ID. Unknown later fields never erase confirmed immutable lineage, and confirmed lineage enriches a native read that omits it. A contradiction uses JG_AGENT_HQ_PROVIDER_FAILED.

## File inputs and complete results

Text and native skill inputs accept optional `files: [{ path, mediaType }]`. Paths may be absolute or relative to the managed workspace and must resolve inside an operator-authorized root. The runtime opens a checked regular-file descriptor, validates UTF-8 or the declared format signature, and binds the canonical path, byte count and SHA-256 before admission. It rereads and verifies that binding immediately before native delivery. Missing, changed or escaping queued files fail without sending input. Symlinks cannot redirect delivery outside the trusted roots. URLs are never fetched.

The fixed limits are 8 references, 16,777,216 aggregate file bytes and 262,144 bytes per UTF-8 text file. Empty files, NUL-containing or invalid UTF-8 text, wrong signatures, unsupported media and oversized input are rejected. The 32,768-byte action envelope contains references, never base64. File bytes are encoded only inside the native 32 MiB frame; the file limits leave room even for worst-case JSON escaping.

Codex supports PNG, JPEG, WebP and UTF-8 text. Images use native `image` data inputs; text files become complete text inputs labeled with their canonical path and hash. Claude supports those formats plus GIF and PDF at turn start, using native image/document blocks. Media signatures establish the declared format, not complete image/PDF validity; native decoder or model rejection remains a provider failure. `capabilities.inputSchema` includes `supportedMediaTypes`, `steerMediaTypes`, `maxFiles`, `maxFileBytes` and `maxTextFileBytes`. Native model-specific media limitations remain native errors.

Select a bounded JSON `outputSchema` in session settings or, for Codex, on a message/queue entry. Schemas are limited to 8,192 serialized UTF-8 bytes, 16 levels and 1,024 visited nodes, and must be supported by the installed Zod JSON Schema validator. External references are rejected and no remote schema is retrieved. Codex sends the selected schema as `turn/start.outputSchema`. Claude starts its owned structured process with `--json-schema`; a different schema requires close and explicit resume of the same native session. Its capability descriptor marks this as `idle-restart`.

Selected action receipts expose nullable `result: { state, format, text, structuredOutput, isComplete, failure, usage }`. Results come from the complete native final message/result, independently of the 65,536-character history/live preview. The serialized result budget is 8,257,536 UTF-8 bytes, which leaves room in the 32 MiB IPC frame for action and transport metadata. Structured results retain the complete parsed value with `text: null`, avoiding a second escaped copy of the same JSON. This admits a 1 MiB UTF-8 result even when JSON escaping expands its content. The runtime validates native structured output against the requested schema without stripping fields. Invalid or missing schema output fails the turn; oversized capture fails explicitly with no saved excerpt. Invalid but bounded JSON remains untrusted evidence in `structuredOutput`. The result is saved with native turn completion, survives a runtime restart and is omitted from action-list reads.

`failure` is null or `native-error`, `invalid-structured-output`, `result-too-large`, or `missing-result`. A native turn can complete without a final assistant message; without a requested schema, that remains completed with `isComplete: false` and `missing-result`. It cannot supply a complete report. Interrupted native execution remains interrupted unless capture itself exceeds the result budget. None of these outcomes causes automatic replay.

`usage` is nullable and contains known `inputTokens`, `outputTokens`, `cachedInputTokens` and accounting `scope`. Built-in adapters expose per-turn observations, not billable counters; missing or malformed optional usage is unavailable without invalidating essential completion evidence. Native MCP/dynamic tool calls and Claude tool blocks appear as bounded `tool` items. Truncation and live gaps remain explicit. Complete final results are authoritative retained records, not a parallel conversation cache.

Steer file eligibility comes from the additive `inputSchema.steerMediaTypes` array on provider and session capabilities, a subset of general `supportedMediaTypes`. An empty list permits no files; consumers must treat absent or malformed metadata as unknown before canceling queued work. Codex lists PNG, JPEG, WebP and UTF-8 text, and reuses its turn-start input items. Claude lists PNG, JPEG, WebP, GIF and UTF-8 text. Its steers encode text files as `File <path> (SHA-256 <hash>):` followed by a newline and content, alongside native image blocks; PDF steers are rejected as a whole before writing. Claude's ordinary text/PDF document blocks at turn start are unchanged. File count, individual/aggregate bytes, workspace/link restrictions, hash binding and identical replay semantics match message and queue inputs. No attachment bytes are reread on an already admitted identical replay.

## Claude history

Visible Claude queued prompts (`attachment.type: queued_command`, `commandMode: prompt`) appear as user-message items; hidden meta records retain their exclusion. The graph UUID remains the history address; the validated `source_uuid` names the input for provenance, and its original first text block supplies `nativeInputSha256`. They inherit the running turn. New Claude steers use the exact action UUID as their wire UUID; exact acknowledged provider/session/hash/target matches can establish host or browser provenance, including a late ordinary-user replay whose own UUID becomes its turn. Legacy unrelated UUIDs remain unknown. Projection version 12 rebuilds cached version-10/11 indexes within the same budgets, preserving 13.1.5 queued-record-before-parent handling; no storage migration or transcript rewrite is required. Saved queued messages reconcile their live replay only when source UUID, hash, turn and normalized body match.

Claude connects as the runtime starts through `claude --print --input-format stream-json --output-format stream-json --verbose`. No user prompt, bare mode, permission bypass or SDK dependency is used. Runtime status reports this adapter as `idle`, `ready` or `unavailable`, with its observed CLI version. History reads need this process only until it has once started and initialized, which the runtime's start-time warm-up does: the runtime keeps that check, so history reads use the transcripts alone, while usage, models and other reads that use the connection still open it. This session-less process closes after 5 minutes without a read and opens again on the next read that needs it; while it is closed, status reports `idle` with the last observed version. An unavailable native lane requires restarting the host after resolving the native problem.

The structured CLI interface has no session-history listing operation. The Claude-owned reader therefore uses direct UUID JSONL files in the native project's directory beneath `CLAUDE_CONFIG_DIR`, or the normal `.claude` directory. CLI and transcript version labels do not gate reads. Required session identity, workspace, parent links, timestamps and message roles are validated, while additive fields and mixed version labels are tolerated. Claude Code can write a hidden record, such as an attachment or a scheduled-task event, a few lines before the record it follows; the reader holds it back until that parent is indexed. An indexing batch that ends between the two leaves the hidden record to the next batch, so they stay in one turn; one whose parent the transcript doesn't hold yet, or that a whole batch from it doesn't reach, starts a turn of its own. A message whose parent is unknown is never accepted. Encoded project keys longer than 200 characters, directory/file links, malformed required fields and records larger than 32 MiB report unavailable. Discovery never recurses into subdirectories, including excluded directories. Unsupported discovered sessions have `historyState: unavailable`; they do not prevent supported sessions from being listed.

Discovery verifies the workspace recorded inside each transcript before returning its identity or title. A matching native directory name alone is insufficient because punctuation replacement can produce colliding directory keys, so a transcript belongs to the selected workspace once one of its records ran there: in the workspace or a subdirectory, including a removed one, whose nearest existing path ancestor resolves inside the workspace without excluded segments. A symlink escape doesn't count as inside. The session's other records may name any other folder, such as a sibling task worktree it moved into, and are listed and read with the rest. Every record must carry the session's own ID, and no record's folder, nor its nearest existing ancestor's real path, may have an excluded segment; otherwise the history is unavailable. A transcript with no record inside the workspace is omitted until one is written. If a file's workspace cannot be established, discovery reports unavailable rather than inventing an empty result.

The existing SQLite worker incrementally records file identity, complete-line offsets, message identities and parent links. It does not save message bodies. File identity includes the current reader projection revision and a native prefix hash, so source changes invalidate the derived projection. Each worker batch inspects at most 128 directory entries and reads at most 8 MiB of new transcript bytes, one file at a time, so one batch takes well under a second; a batch whose first record is larger reads that record whole, up to the 32 MiB record limit. A batch that stops before the end leaves the rest to the next one, which continues where it stopped, unless a transcript was added to or removed from the directory since its scan began, which starts the scan over. The adapter continues batches with a host-event-loop yield between them, within a 30-second operation budget. If that budget is reached, the read reports unavailable and subsequent reads continue indexing. At most four incomplete discovery iterators remain open. Shutdown closes them. A discovery page that continues a folder's list after its first native page uses that projection without starting another directory scan; start a fresh first page to refresh discovery. A transcript whose identity, size and modification time match a projection that reached its end is neither read nor written again. Each directory scan keeps the transcripts it has seen in memory, and only a complete scan removes the others from the projection, so reads over unchanged transcripts write nothing to SQLite. No additional cache infrastructure or browser cache is used.

Current-chain membership and turn starts are indexed as metadata. Item continuations seek those indexes; they do not walk the full chain per page. A changed branch rebuilds membership before exposing that revision. Repeated native message identities can replace content while retaining their parent; a changed parent for the same identity is an unsupported format.

Selected history reads refresh only that file, retain incomplete tails, and detect truncation or replaced identity. Changed branch/file revisions invalidate item continuations. Only the current parent-linked conversation chain is returned. A compaction's boundary has no parent and names the record before it, which the chain follows back to the start of the conversation; when the transcript holds no such record before the boundary, as in a chat Claude Code moved into a new session, whose boundary names the old session's record, the chain starts at the boundary. Claude Code links each tool result to its own call, so parallel calls whose results finish out of order would leave the later calls and results on a side branch; such a result follows the latest record of its call's turn instead, keeping every call of the response and all their results on the chain without changing its revision. Text is reread from the native file for the selected page and normalized as plain text. Thinking blocks are left out, and a record holding only thinking is hidden, as are `<task-notification>` records and a subagent's sidechain records. A message Claude Code takes into a running turn, such as a steer it takes in at a tool boundary, is saved as a `queued_command` attachment instead of a user record; it is a `user-message` of that turn whose `provenance.nativeInputId` is the native input the attachment names, and other queued commands, such as background task notifications, stay hidden. Live items leave a subagent's stream frames out likewise, and those frames start no turn, though a subagent's tool results still settle the approvals it asked for. Compaction summaries, `<local-command-stdout>` output and interruption markers are `notice` items, and a slash command is a `user-message` reading `/name args`. A `!` shell input and its output are `command` items, the output's `callId` being the input's UUID. A tool call shows its native name and input, with the block's ID as `callId`, which is null for a record calling several tools; its result is a `tool` item carrying that ID, `failed` when it has `is_error` and `succeeded` otherwise. An Edit or Write result whose metadata has a `filePath` and a `structuredPatch` is a `file-change` item reading the path and its patch lines, or a created file's content, every line of which counts as added. A result Claude Code saved to a file reads `Output too large (<size>), saved to a file` followed by its preview, without the file's path. A result made of content blocks, such as a screenshot with its caption, reads as its text blocks, each image as `[Image]`. Other non-text content has explicit native block labels. The index stores each entry's presented kind and visibility, so evidence kind filters match `items` and hidden records never shorten a page. An unknown record containing content is returned as an `unsupported` item when its identity and chain are trustworthy; it cannot imply an agent response, idle state or completion. Each selected page reads at most 4 MiB of record bytes beyond its first record and returns at most 4 MiB of serialized item presentation, so a large-text page can contain fewer rows than its requested limit.

File timestamps and records do not prove that a native process is idle or a turn completed. Claude file-backed thread and turn states are therefore `unknown`, with no invented completion timestamp. Explicit native custom titles are preserved; a missing title remains null. A turn starts at a message the operator sends, including a slash command, except a message taken into a running turn, which belongs to it; task notifications, compaction summaries, local command output, interruption markers and `!` shell records belong to the turn before them. Grouping follows parent links and is not an authoritative execution boundary. A compaction starts a new chain whose first record names the record before it, so history reads on past the compaction to the start of the conversation.

## Async questions

An explicit Codex `agentMessage` with `delivery: 'async'` carries optional `asyncInput` on its normalized history item. The same metadata is available in live items, item details and every evidence fragment. Ordinary messages have no `asyncInput`; text or a `questions` field alone never establishes async semantics.

Available metadata is `{ delivery: 'async', state: 'available', questions }`. Each ordered question has a nonempty `title` and optional ordered string `options`. Question and choice strings retain their exact content, up to 8192 UTF-16 code units each, with at most 32 questions and 32 choices per question. The entire normalized `asyncInput` must fit `MAX_ASYNC_INPUT_BYTES` (32768 serialized UTF-8 bytes, including JSON escaping). Additive native fields are tolerated. Malformed contracts retain ordinary preview text and `{ delivery: 'async', state: 'unavailable', reason: 'invalid' }`; valid shapes over the byte budget use `reason: 'too-large'`. Choices are never shortened to fit a response. Evidence fitting accounts for metadata before selecting its text chunk; live memory accounting includes the complete serialized item, and saved/live reconciliation requires matching async metadata.

`hq.observeAsyncInputs(listener)` is a trusted in-process Node API, independent of IPC/browser readers. It returns an idempotent unsubscribe function. The listener synchronously enqueues bounded host work; it must not block, return asynchronous work or use observations as authority. An `item` event contains `source: { threadId, provider, nativeId, workspaceRoot }` and the complete normalized `item`. `threadId` names the managed record. Only completed items from controlled sessions with a validated source are emitted; partial updates and external sessions are excluded. Each listener receives its own copy.

A `recovery` event contains `provider`, nullable `source` and `reason`: `subscribed`, `output-gap`, `reconnect` or `listener-failed`. Subscription immediately requests catch-up for managed Codex sessions. A null source means recovery for that provider's relevant controlled sessions. Native connection/output loss requests catch-up, and successful reconnect requests it again. Listener exceptions cannot stop native execution or other subscriptions: recovery is attempted immediately and, if the listener still fails, before its next observation. There is no callback queue, replay log or persistent question store. Runtime shutdown releases all listeners; subscribing after shutdown retains none.

Hosts retain their own resolution metadata and recover missed questions through bounded authorized `items` pages, deduplicating by exact session/turn/item identity. A question can remain unresolved after its native turn finishes. It is separate from a blocking native `item/tool/requestUserInput` approval and is never answered with `native-reply`. Only explicit authenticated host input authorizes an ordinary message or exact-turn steer. Async messages are excluded from ordinary final-result capture before phase and size handling; an async-only turn retains the existing `missing-result` outcome.

## Thread control and live input

A new UUID with an expired epoch cannot execute.

Message and queue input is a closed union: `{ kind: 'text', text }` or `{ kind: 'skill', skillId, arguments }`. A selected skill is resolved through the target thread's current native catalog before admission. Unavailable, missing or disabled selections cannot dispatch. Normal text needs no catalog read. Steering retains its `text` field and exact active-turn target, adding only optional top-level `files`. Text-only steers remain unchanged; skills and turn settings cannot be steered.

Names use lowercase ASCII letters, digits and hyphens, start with a letter or digit, and have at most 64 characters, the public `MAX_THREAD_NAME_LENGTH` from `jg-agent-hq/contracts`. The same bound applies to create, adopt, rename and managed-thread responses. Names are unique without regard to case in one state directory. Creation and adoption resolve collisions atomically with ordinal suffixes such as `build-usage-2`, truncating the base to keep the complete name within 64 characters. Explicit rename rejects an occupied or pending name. Provider/native-session pairs remain unique. At most 32 native sessions are controlled concurrently; close idle sessions to release capacity. Native discovery remains independent of that limit. Confirm that other native CLI controllers are closed before adoption, resume or recovery. An unloaded native status cannot prove another CLI has stopped. The runtime provides exclusive coordination within one canonical state directory; it does not impose a global lock on independent CLIs. Recovery is permitted only after the producing runtime has stopped and its ownership evidence has been inspected.

Version 13 expands the producer contract: a 12.x consumer's strict 32-character schema rejects a response containing a longer managed name. Run matching runtime and consumer releases. Storage remains compatible with 12.0.1, but a package downgrade first requires shortening all longer managed names with supported rename actions and resolving collisions; see [package downgrade](../docs/recovery.md#package-downgrade).

Codex may keep an idle native thread loaded after `thread/unsubscribe`, as when a terminal still holds it. An explicitly confirmed resume may reacquire that thread when its known managed control is inactive and managed, without settings overrides. Ordinary resume still refuses active native threads, uncertain managed ownership and already controlled idle sessions.

After the producing HQ runtime stops, explicit `thread-recover` with `recovery: { kind: 'resume' }` may also rejoin that managed record's known Codex identity while it remains loaded idle or active. The operator must inspect its ownership evidence and stop competing controllers that could submit work. HQ reads its current native turn, binds it before joining so reissued approvals find their turn, then verifies the same turn again before acknowledging recovery. It changes no settings, sends no input, leaves earlier queued entries paused and does not resolve uncertain input receipts. Unknown execution state, a mismatched workspace/identity or a changed turn refuses recovery. Uncertain ownership from the current HQ runtime still requires that runtime to stop first. Recovery that attaches an identity after uncertain creation and ordinary adoption retain their existing unloaded-session checks.

Receipts separate `delivery` (`queued`, `submitted`, `acknowledged`, `uncertain`, `failed`, `canceled`) from nullable native turn `completion` (`completed`, `failed`, `interrupted`). Acknowledgement means the exact native request was accepted, not that the turn or tool completed. Permission replies remain submitted after a pipe write and become acknowledged only when Codex resolves the exact native request or Claude returns a tool-result block for the exact tool-use identity. Claude cancellation expires the prompt and leaves an unacknowledged written reply uncertain. Resolution does not prove a tool ran. The receipt includes managed and native identity, its nullable `provider`, digest, timestamps, safe failure classification and optional related action. Its `phase` is the native step the action takes now: `create`, `resume`, `name`, `turn`, `steer`, `interrupt`, `clean`, `close`, `delete` or `reply`. A create continues with `name` once its session exists, and with `turn` when it carries a first input; a close's `interrupt` continues with `clean` once the turn ends, and its `clean` with `close`; a deletion of a session the runtime runs takes `clean` and `close` before `delete`. An action that sends nothing native, such as queued input before it is sent, has none. Only selected receipts expose `nativeThreadId`, the native session of the action's thread once the runtime records it, undelivered `queuedInput` and the nullable complete native `result`; collection reads omit all three. Queued input retains prepared text, native skill identity, content-bound file references and explicit turn settings, never file bytes or skill content. It is cleared after delivery acknowledgement or cancellation.

A missing acknowledgement never triggers an automatic resend. Exact late responses reconcile delivery, including completion that arrived first. Native output loss marks the affected provider controls and submitted work uncertain. A Claude process failure affects its own session; a Codex transport failure affects its Codex cohort. Restart quarantines controls from an interrupted runtime, except the Codex sessions the next runtime rejoins; explicit recovery preserves the managed identity and name. Successful shutdown proves native process-group exit before marking Claude controls inactive. Unknown creation without a native identity remains uncertain.

Saved Claude input can acknowledge a submitted or uncertain steer without a live replay, including after restart. Authorized `items`, `item-detail` and `session-evidence` reads and the existing bounded turn-completion history flush match the exact source/action UUID, provider, native session, workspace, original target turn (or the steer's own follow-up turn) and full original-text SHA-256. Failed/canceled actions, mismatches and live-only presentation never establish this confirmation. Confirmation wakes receipt waits and refreshes live provenance; it changes neither control ownership nor completion, dispatches no work and restores no queued readiness. It reuses selected history pages and indexed action lookups without new scans, caches, storage or polling.

Normal native turn completion may advance ready queued entries once, in creation/UUID order. Failure, interruption, explicit interrupt admission or restart pauses the queue. A rejoined Codex session's queue advances again once the turn it waits on completes. Permission prompts do not advance it. An unacknowledged start or metadata change blocks dependent starts until its outcome is reconciled or the stopped runtime is recovered explicitly. A turn's completion alone does not settle an unresolved steering receipt.

Native replies use one of these closed response forms:

- `{ kind: 'decision', decision: 'accept' | 'acceptForSession' | 'decline' | 'cancel' }` for command/file approval, restricted to the choices Codex offers.
- `{ kind: 'permission', decision: 'accept' | 'decline', scope: 'turn' | 'session' }` for additional permissions. Acceptance copies only the complete displayed native scope. Unknown permission fields cannot be approved.
- `{ kind: 'answers', answers: { [questionId]: [answer] } }` for native questions. Every requested question must have an answer; `allowsMultiple` indicates whether several answers are allowed. Codex questions accept one answer, and predefined choices are enforced when free text is unavailable.
- `{ kind: 'elicitation', action: 'accept' | 'decline' | 'cancel', content }` for MCP forms and URL requests. Accepted forms require an object matching the exact native JSON Schema. URL acceptance, decline and cancellation require `content: null`. Responses never open a URL or fetch a schema.

Approval records expose `replyActionId` as soon as a reply is admitted, so reconnecting clients can read its receipt and avoid offering another answer while native resolution is pending. `approvals` accepts `threadId`, optional `state`, `limit` (default 32, maximum 128) and a query-bound `cursor`; it returns `{ data, nextCursor }` in descending `(createdAt, id)` order. Indexed seek reads do not load the complete history. State filters are live views, so refresh the first page to observe new records or transitions above a continuation position.

Each record contains identity, `kind`, `isBlocking`, `state`, `replyActionId`, timestamps and nullable `presentation`. Presentation contains the complete native title, detail, decisions, questions and optional elicitation metadata. It is available only for a matching live pending request. Resolved or expired records retain metadata after reconnect and restart, with `presentation: null`. Restart and native disconnect expire pending requests; they never recreate response authority. `expired` means the request is no longer answerable, not that a submitted response was rejected. Prompt bodies and answers remain in memory. SQLite retains only native request identities scoped to their managed thread, scope fingerprints and reply receipts. Fingerprints use a per-store HMAC key in the private 32-byte `action.key`. Keep that file with the database; a missing, invalid or mismatched key on a nonempty store fails closed. Ordinary input bodies are not saved by the runtime. Undelivered queued inputs are saved until acknowledgement or cancellation. Complete native final results are retained on the selected action receipt; streamed token and tool-output bodies remain native.

### First input

A `thread-create` with `input` admits the input as a `message` would: its files are read and bound to their content, a skill resolves from the folder's catalog, which gives a skill the ID the new session's catalog gives it, and Codex refuses PDF and GIF files, all before any session starts, so a refused input creates nothing. The admitted input waits on the action as its `queuedInput` until it is delivered. Once the session exists and is named, the same action starts its first turn, in phase `turn`, with the session's startup settings; it settles, `acknowledged`, once the turn's input is acknowledged, carries the turn's `nativeTurnId`, `completion` and `result` like a message's receipt, and the session's transitions are `opened`, then `turn-started`. When the first input fails after the session was created, the session stays created and named, and the receipt fails or turns uncertain in phase `turn`, keeping its `queuedInput`, as a message's would: the session then needs recovery before further native controls, as after a refused message. An authenticated browser submission of the create records the new session as its selected thread, so its first message has operator provenance.

### Thread deletion

`{ kind: 'thread-delete', provider, workspaceRoot, nativeId }` deletes a session no process runs, managed or not, and the runtime's records of it, and runs within its request: it resolves to the settled receipt, `acknowledged` with `threadId` and `nativeThreadId` null, or throws why the deletion failed after recording its receipt as failed. Repeating the request returns its receipt.

The folder must be inside the allowed roots, or the request fails with JG_AGENT_HQ_TARGET_FORBIDDEN. It is refused with JG_AGENT_HQ_REQUEST_INVALID, before anything is recorded, for a session a process may run: one the runtime's records or observations show running, waiting or held idle by another client, a Claude session a terminal runs, a managed session the runtime recorded in another folder, and a managed session that is neither closed nor, under this runtime, idle with no turn and no action in flight, such as one whose ownership is uncertain. A managed session the runtime runs idle is closed first by the same action, in phases `clean` and `close`, as `thread-close` closes it. A Codex session the runtime doesn't manage is read from the daemon first, which checks its folder, failing with JG_AGENT_HQ_TARGET_FORBIDDEN when it ran elsewhere, and refuses one a client has loaded.

- **Codex**: The runtime asks the daemon to delete the session with `thread/delete`, Codex's own deletion, and touches none of Codex's files. A session Codex never saved, such as one created without a turn, which Codex answers with `no rollout found`, counts as deleted.
- **Claude**: The runtime deletes the session's transcript, `<id>.jsonl`, and the folder beside it that holds its subagents and saved tool results, in the project directory of the workspace, without following a link at either path, then forgets the transcript in its history index. A path that doesn't exist is already gone. A session ID that isn't a UUID, as Claude's are, is refused with JG_AGENT_HQ_REQUEST_INVALID.
- **Records**: The runtime deletes the session's observed-session record and, for a managed session, its approvals, the host receipts of its actions, its actions and its thread, keeping the deletion's own receipt. The transition log keeps the session's transitions, which leave it after seven days like any other, so a reader following it sees no gap.

A deletion whose `delete` step fails reports JG_AGENT_HQ_PROVIDER_FAILED, its message carrying the cause, and records the action `failed`, since deleting again is safe; a managed session stays as it was, closed, and the next deletion can try again. A Codex answer that arrives after its request's deadline changes nothing. A failure while the deletion closes a session the runtime runs reports that step's own error and leaves the session as a failed `thread-close` would.

### Claude native control

Idle local-command and settings user replays do not start inference or acknowledge a pending input. They remain in native saved history. A controlled input starts only on its matching replay or result; an autonomous turn starts on model output. This keeps model changes from introducing a phantom turn that would reject the next input's acknowledgement.

Each controlled session has one native `claude` process in the authorized workspace while it is in use. A session idle for 60 minutes since its last turn ended, or since it opened, gives up its process: the runtime reads its native settings once and closes the process, and the session stays idle with no state transition. Its skills and configuration reads answer from what it kept, an interrupt is refused as for any idle session, and stopping or releasing it needs no process. Input and renames first reopen it with `--resume`, or `--session-id` when it never had input, and its kept settings. A parked session keeps its controlled-thread slot, of 32 per runtime, and a runtime restart treats it like any other managed Claude session. A running or waiting session is never stopped, and neither is one with a background command still running, as Claude's `system:background_tasks_changed` list reports it, since closing its process would end the command; it waits another idle period instead. The runtime adds structured input/output, replayed user-message acknowledgements, partial-message output and `--permission-prompt-tool=stdio`. It applies only explicitly selected startup options, including model, instructions or an output schema. It preserves normal native settings, session persistence and permission handling. Native skills remain available. Native idle initialization, session identity and matching acknowledgements establish capability. Version labels and missing diagnostic version metadata do not disable compatible controls or file history.

Creation chooses a native UUID without inference, then names that exact session. Resume uses native `--resume` and verifies the session-id fence on the name control before marking the session idle. The operator's handoff confirmation establishes that another CLI controller is closed; file timestamps and file-backed unknown states do not establish this. Independently running CLIs are outside the runtime's state-directory coordination boundary.

An ordinary message is submitted only while idle. Its native UUID becomes the turn identity. A matching native replay or result acknowledges delivery, and the native result establishes completion. A request-success envelope can acknowledge a name change or interruption without a response body. The runtime never writes queued follow-up input into Claude's own busy queue; the runtime's shared queue dispatches it only after the previous result. Interruption acknowledgement alone does not establish a stop. An error result is classified as interrupted only when the qualified native interruption marker was observed for an explicitly interrupted input. Other terminal errors remain failed.

Claude also starts turns of its own while no runtime input's turn is active, such as after a background command finishes. Claude sends no user message for such a turn, so the runtime records it under an ID it generates: the thread reports running from the turn's first frame, its items stream as live items under that ID, its permission prompts are presented and answered like any other, Stop interrupts it, and its result completes it without a captured result, since no action owns it. Input sent while it runs waits in the runtime's queue. Input written just before it began is replayed by Claude after its result, as its own turn with its own result; when that turn outlasts the 30-second acknowledgement bound, the input's receipt is uncertain until the replay acknowledges it. A frame that fits none of these rules still makes the session unavailable.

Claude questions use exact question text as their answer identity and expose whether multiple selections are supported. Claude can_use_tool permissions use response `{ kind: 'decision', decision: 'accept' | 'decline' }`; question replies use `{ kind: 'answers', answers }`. The response kind `permission` with a turn/session scope belongs to Codex additional permissions. Tool permissions offer `accept` or `decline` for the displayed input only. Complete request details include native policy hints and reasons as untrusted display data; none authorizes a response. Fields Claude adds to a permission request that the runtime doesn't list are dropped, so the request still reaches the operator with its known fields, and the reply still holds only the displayed input. Unsupported interaction surfaces receive the error `jg-agent-hq couldn't present this request`, which Claude records as the tool call's failed result. Requests requiring a native interaction card cannot be answered with generic approval; supported `AskUserQuestion` cards use their typed answer contract. Session-wide permission changes are unavailable; the runtime does not apply native permission suggestions automatically. A reply is written through the separate control channel and acknowledged only by the matching tool result. Tool execution can still fail after that acknowledgement. Reused raw request IDs in different CLI processes have distinct controller scopes. Prompt bodies and replies remain out of SQLite.

Both providers support turn-correlated MCP `form` and `url` elicitation. Forms use bounded local JSON Schema validation (8 KiB, 16 levels, 1,024 nodes); responses stay within the action envelope’s 32 KiB budget. Unknown modes, unsupported schemas and Codex requests without a native turn are denied. Elicitation URLs are HTTP(S) links without embedded credentials; applications decide how to display or open them. Never render native strings as HTML or terminal instructions, and never infer a permission decision from model output or form metadata. Codex acknowledges an elicitation reply through its exact native request-resolution event. Claude supplies no equivalent form-reply acknowledgement: a successful write stays submitted, and terminal completion or cancellation expires the request and makes its unresolved reply uncertain. Retrying that same action returns its receipt without sending again.

Partial text uses temporary live identities until the final native message UUID arrives; that replacement shares the existing global live-item budget. Live frames and streaming previews follow the history presentation: thinking is left out, task notifications aren't shown, and a live Edit or Write result is a file change. Persisted history reconciles matching final items through the same content normalizer. Closing the session proves owned process-group exit, including native background children, before the runtime releases control.

## Native skill catalog

`skills` accepts `provider`, `workspaceRoot`, an optional managed `threadId`, optional `search`, `limit` (default 32, maximum 128) and `cursor`. The folder must be inside the allowed roots. With `threadId` it reads that controlled session's catalog, and the session must run for that provider in that folder, or the request fails with JG_AGENT_HQ_REQUEST_INVALID; it never adopts or resumes an external session. Without `threadId` it reads the catalog a session started in the folder would have, with no session: Codex lists the folder, and Claude starts a session-less read process there with the trusted additional directories, reads its initialization command list and closes it, without a user prompt or model turn. A skill's ID is derived from its provider, name and path, so a folder's catalog and a session started there give the same skill the same ID while the skills don't change, and an ID from the folder's catalog can name a skill for that session's input. Codex uses native `skills/list` for the workspace, plus the skills in the operator's Codex extra roots; Claude uses the native initialization command list, which includes explicit-only skills. Its refresh endpoint omits those skills, so the runtime does not use it. Close and explicitly resume the session to refresh Claude's catalog. Inactive or unsupported sessions report `unavailable`, with no successful-empty fallback. Native discovery errors produce `partial` and an `unavailableCount`. `observedAt` records when the native inventory was observed; it stays fixed for a Claude session and is null when unavailable. `invocationPrefix` is the text that starts a skill invocation in the provider's native input, `/` for Claude and `$` for Codex, and is null when unavailable; a provider adapter supplies it with its inventory in `IProviderSkills`, from `readSkills(workspaceRoot, nativeId, call)`, which reads the folder's inventory when `nativeId` is undefined.

Rows contain an opaque `id`, native `name`, `description`, nullable `argumentHint`, `kind`, `path`, `scope`, `prerequisites` and `requiresExplicitInvocation`, plus native availability as `isEnabled`. Codex supplies skill identity, source/scope, enabled state and declared tool prerequisites, but no argument hints, so the runtime reads each listed skill's single-line `argument-hint` frontmatter from the `SKILL.md` at its reported path, 8 files at a time: a regular file of at most 65,536 bytes, without following a link at that path. A hint that is missing, empty, a block scalar or over 1,024 characters is null, and a file the runtime can't read leaves only the hint null, without counting toward `unavailableCount`. Claude supplies native command names, descriptions, argument hints and a built-in marker when available. Other missing fields are null or `kind: 'unavailable'`; the runtime reads skill files only for those Codex hints and for Codex extra roots, which native discovery does not list: the runtime reads each skill's single-line `name`, `description` and `argument-hint` frontmatter from `<root>/<directory>/SKILL.md`, reports it with scope `host`, skips linked directories and files, and counts unreadable entries in `unavailableCount`. A native skill with the same name takes precedence. Declared prerequisites are metadata, not proof that an integration is connected. Invocation rules remain with the CLI, including explicit-only skills.

Both native inventory interfaces are unpaged. The runtime accepts at most 4,096 native rows and 1 MiB of normalized catalog metadata per read, then provides stable ID seek pages guarded by the complete inventory revision and query. A changed inventory invalidates continuation. Only metadata is read, never skill bodies or complete conversation histories. Concurrent reads of the same session, or of the same provider's folder, share their in-flight native request; Codex results are not retained as a runtime cache. Claude's native initialization metadata remains attached to its owned connection until that session closes. Native refresh and discovery caches remain provider-owned.

A skill input resolves its exact invocation from the session's current catalog before admission. Codex receives `$name arguments` with an explicit native skill selection containing its native name/path alongside that text. Claude receives `/name arguments` and performs native slash-command loading. Native same-name precedence applies. A missing, disabled or unavailable selection sends nothing. Explicit message and queue actions share the established action ledger, ownership checks and delivery/uncertainty rules. They grant no tool permissions and do not expand the invoked workflow's authority.

Trusted runtime construction also accepts `codexExtraSkillRoots?: string[]` and `claudeAdditionalDirectories?: string[]`. Paths must resolve to existing absolute directories. Codex receives them as capability roots of each thread the runtime starts, so other sessions on the shared daemon, including terminal sessions, never see them. Forks inherit them. A session Codex later reloads from disk loses native discovery of those skills, while explicit invocation through the runtime's catalog still works, because it names the skill file. Claude sessions and every folder-scoped read process receive native `--add-dir` arguments, which also grant native file access to those directories. These inputs belong to the operator and cannot be changed through IPC commands. The installed `serve` command exposes repeated `--codex-extra-skill-root` and `--claude-additional-directory` flags. No global skill installation or coding-instruction change is performed.

`codexDaemonLauncher?: string[]`, also trusted, names a command and its arguments that run `codex app-server daemon start`, such as `['systemd-run', '--user', '--scope', '--quiet', '--collect']`. The runtime runs the start through it, while the proxy still runs directly. Codex's daemon detaches into its own session, but on Linux it stays in the cgroup of whatever started it, so a host that runs as a systemd service and starts the daemon itself would take the daemon, and the work of every terminal session on it, down whenever the service stops. A new scope gives the daemon a lifetime of its own. The installed `serve` command doesn't expose it.

`isPreviousRuntimeStopped?: (owner: { pid: number; createdAt: string }) => Promise<boolean>`, also trusted, lets startup recover a state root a runtime left behind after an unclean exit, such as a crash or a SIGKILL. It is called with the `runtime` lock's owner, its process ID and the time it took the lock, only when jg-locks reports that owner's process gone (`owner-gone`), and must resolve true only when no process of that runtime remains, for example because the service's cgroup holds only the caller and its descendants. Startup then takes the lock over from exactly that owner with jg-locks' `recoverFrom`, which fails when another process took it first; in the same step it takes over and releases a `snapshot` lock the same process left, and removes a leftover `hq.sock`, only when it is a socket and not a symbolic link. When the owner's process exists, its record can't be read, no check is supplied, or the check resolves false or rejects, startup fails with JG_AGENT_HQ_RUNTIME_ALREADY_OWNED, with a rejected check or jg-fs' busy lock as the private cause. The installed `serve` command doesn't expose it.

`{ kind: 'action-wait', actionId, until, timeoutMs }` waits on one receipt instead of polling `receipt`, and returns `{ receipt, isTimedOut }`. `until: 'native'` returns once the receipt has a `nativeThreadId`, as soon as the runtime records a created session's native ID, and `until: 'settled'` once its `delivery` is `acknowledged`, `uncertain`, `failed` or `canceled`, which only late native evidence or an operator's recovery changes. A `native` wait also returns once the receipt settles without a native thread ID, such as after a failed creation, because nothing can then give it one. `timeoutMs`, from 1 to 30,000, bounds the wait; when it passes first, the receipt comes as it stands with `isTimedOut: true`. An unknown action returns a null receipt at once. The receipt's workspace is authorized as for `receipt`. The runtime reads the receipt again only after the actions module records a change that can affect it, never on a timer. A wait still running when the runtime starts closing ends at once with RUNTIME_NOT_RUNNING. A wait is admitted work, so `withStorageMaintenance` waits for it to end, and over IPC it holds one of the 32 connections; its 30-second limit, `MAX_WAIT_MS` in `jg-agent-hq/contracts`, fits the 35-second IPC deadline.

`textLimit`, from 1 to 65,536 and 65,536 by default, cuts each item's text on `live-items`, and each queued text on `actions`, to that many UTF-16 code units on a code-point boundary, marking it `isTruncated`, as `items` cuts history. On `actions` it cuts only the page, so a continuation may change it.

### Long-polls

`session-states` and `live-items` take `waitMs`, from 1 to 30,000, and then wait for a change instead of answering with none, the way `action-wait` waits for a receipt. A `session-states` long-poll answers at once when transitions follow `afterSequence`, or `isReset` is true, and otherwise once a transition is recorded; when `waitMs` passes first, it answers with its empty page. A `live-items` long-poll answers at once without `afterRevision` or when the window's revision differs from it, and otherwise once the window changes; when `waitMs` passes first, it answers `unchanged` with no items. A thread without a native session yet has no window, so it answers at once. Without `waitMs`, both answer at once.

The runtime's own changes wake them, never a timer: the store worker reports the highest transition sequence after each call, and a call that recorded a transition wakes the `session-states` long-polls, which read again; every change of a live window wakes the `live-items` long-polls on that window, or on every window when it can change any window's revision, which read the window from memory again. A long-poll is admitted work, like `action-wait`. At most 32 long-polls wait at once in a runtime, as many as IPC accepts connections; another fails with JG_AGENT_HQ_ACTION_CONFLICT, and each one that ends frees its place. A long-poll still waiting when the runtime starts closing ends at once with JG_AGENT_HQ_RUNTIME_NOT_RUNNING.

The installed CLI exposes `suggest-thread-name --topic <topic>`. Suggestions normalize punctuation to hyphens, keep at most 32 characters, and use `session` when the topic contains no ASCII letters or digits. Creation checks availability again inside its admission transaction. All action targets, histories and relationships continue to use immutable managed and native identities.

Control pages default to 32 and cap at 128. Seek cursors are bound to their complete query and ordering. Reads recheck allowed workspaces. Rejected controls retain their known thread association, and native availability failures appear in each affected thread's replay. Lifecycle replay contains metadata, not token or tool output. Each provider has a bounded native lifecycle backlog; overflow stops that source and marks its state uncertain rather than losing events silently. Live items don't count toward it. The runtime recognizes a repeated lifecycle observation within one runtime; startup forgets the observations earlier runtimes recorded. Other providers retain their independent connection and admission state.

Live item presentation is bounded to 128 items per cached thread, 32 windows and 4 MiB of serialized presentation across the runtime, including escaped text and identifiers. This leaves room inside the IPC response limit. Display text uses the same truncation contract as native history. Eviction, an unavailable window or missing chunks sets `hasGap`. Completed items remain `awaiting-flush` after thread closure until a native history page holds the same item, with exactly matching normalized content or, for an item with an outcome, the same final outcome, or the bounded cache evicts them. A message Claude Code saved as a queued command matches the live input its `provenance.nativeInputId` names. The outcome is enough because Codex shortens long command output when it saves it. An item still streaming when its turn ended, such as a message an interrupt or a Codex steer cut, stays `awaiting-flush` until a native history page holds an item of that turn, since the provider may never save it; the history then shows what was saved of it. A client's `items` read is one such page, and when a turn ends the runtime reads that turn's own history too, newest first and at most 8 pages of 128, until none of its finished items remain, so the window doesn't wait on a client that never reads them. Codex's saved state can trail its turn's end, so a turn whose items remain is read once more 2 seconds later; a failed read leaves them to the next history read. A client that shows live items should therefore expect them to leave the window before its own history read holds them. Read persisted history and the live window together after reconnect; a process restart cannot reconstruct unflushed in-memory content.

Items expose only normalized presentation fields, and one mapping per provider presents `items`, live items and `session-evidence` alike, as the provider's CLI shows them. Kinds are `user-message`, `agent-message`, `command`, `tool`, `file-change`, `notice` and `unsupported`. `callId` pairs a tool call with its result, or is null. `outcome` is `succeeded`, `failed`, or null when unknown or still running. `files` lists each file a file change touched, at most 128, with its added and removed lines, and is empty on other items. `outcome` and `files` come from the full native record, so `textLimit` never changes them. Unknown native kinds report `unsupported` without copying arbitrary payloads. Display text is bounded to 65,536 UTF-16 code units without splitting a surrogate pair; `isTruncated` reports omissions. An unsupported or oversized native transport frame fails explicitly. `createdAt` is the item's time in Unix milliseconds, or null when the provider records none. A Claude item takes its record's `timestamp`, and a live one the time its frame arrived. A Codex item takes its own native lifecycle timestamps, already in milliseconds: operator input prefers `startedAtMs`, and other items prefer `completedAtMs`, using the other item timestamp when the preferred one is missing. History entries and live notifications use the same mapping, with entry/notification metadata preferred over the matching embedded item field. Missing item timestamps remain null; turn times and observation times are never substituted. History pages and item details need no additional turn reads for timing.

Codex leaves `reasoning` items out as it reads them, so a Codex page can hold fewer items than its limit. `contextCompaction` is a `notice` with empty text, because Codex records no summary. `webSearch` and `imageView` are `tool` items reading the query or the image path. A command, file change or tool call takes its `outcome` from its `status`: `completed` succeeded, and `failed` or `declined` failed. `files` counts each change's diff, and an added or deleted file without hunks counts its whole content. A Codex item holds its call and its result together, so its `callId` is null. Claude's rules are under [Claude history](#claude-history).

## Session states

Every session has a live state: `running`, `waiting` (on the operator), `idle`, `closed`, `failed` or `unknown`. A managed session reports it from its managed record. A session another client drives is observed and listed with `ownership: 'external'`; the runtime sends it no input until `thread-adopt` records it as managed, and never stops, wakes or drives a session a terminal runs. A managed session the runtime closed is observed again, so a terminal that continues it shows its state.

A retained session with uncertain ownership also takes its live state from native observation, including loaded Codex sessions found at startup and later status changes. Thread reads, discovery and active-session summaries retain its managed ID and `ownership: 'uncertain'`. Observation never changes its control record, settles uncertain input, advances queued input or restores execution authority. Without a native observation its state remains unknown; explicit recovery is still required to regain control.

A Claude session's summary carries `terminal`: `{ kind: 'interactive' }`, or `{ kind: 'background', attachId }` with the short ID `claude attach` takes, while the latest `claude agents --json` run lists it with a `pid`, and null otherwise; Codex summaries always carry null. While it is set, `thread-adopt` and `thread-resume` of the session, and input to it, are refused with JG_AGENT_HQ_ACTION_CONFLICT, so a session the runtime runs that a terminal resumed takes nothing from the runtime until the terminal closes it. An approval request of a Codex turn reaches every client the daemon serves; when another answers first, the runtime's prompt expires.

Every summary carries `backgroundCommands`, the background tasks the session runs, after which Claude resumes it on its own: commands it runs or moved to the background, and agents it launched there. A session the runtime runs reports the count Claude last reported in `system/background_tasks_changed`, the same count its `live-items` window carries. A Claude session a terminal runs reports the tasks its transcript records since its listed process's `startedAt`, as the active-session poll below counts them. Codex sessions, and Claude sessions no run lists, report 0.

Every summary also carries `continuedIn`. When Claude Code moves a chat into a new session, it ends the old session's transcript with a `continued-in` record naming the new session in `continuedInSessionId`. A Claude session's summary from its indexed transcript carries that session's ID when the record is in the transcript's last 65,536 bytes with no `user` or `assistant` record after it, and the named session's transcript is in the same Claude project directory; otherwise, and for managed, Codex and `active-sessions` summaries, it is null. A session resumed after the move wrote messages after the record, so it continues in none. The answer is kept in memory per transcript, at most 1,024 of them, and read again once the transcript's size or modification time changes.

- **Codex.** The shared daemon broadcasts every thread's status. The runtime records the states of sessions inside the allowed workspaces, reading each session once and keeping the workspace, name and creation time that read found on its observed record, and their items stay readable with `items`. A session already running when the connection opens reports no change, so each time the connection opens, including after a reconnect, the runtime reads the daemon's loaded threads (`thread/loaded/list`, 128 a page, at most 8 pages) and records each one's state from its status. An ephemeral session, which Codex doesn't save, such as a helper session Codex starts itself, is never observed. Observation runs while the Codex connection is open; the connection opens as the runtime starts, and again on the next Codex request after it was lost.
- **Claude.** While the runtime is running, it runs `claude agents --json` every 30 seconds, or every 5 seconds at the `live` pace, each run limited to 10 seconds and 65,536 bytes of output, and joins its entries to Claude discovery by `sessionId`. An entry without a `pid` isn't running, whatever its `state` says, so it counts as missing. Otherwise `status: "busy"` and a background session's `state: "working"` are running, `status: "waiting"` (a question or a permission prompt, for either kind of session) and an interactive `status: "blocked"` are waiting, `status: "idle"` is idle, and anything else is unknown; an entry missing from a run is closed. Entries whose `pid` is a native process this runtime started, its managed sessions and its metadata process, are left out. A failed, late, oversized or malformed run changes nothing. Sessions the runtime manages keep their managed records.

  Before a run records its states, it counts each listed session's background tasks from its transcript. That transcript is the one in the Claude project directory of the entry's `cwd`, or else of the workspace its indexed transcript was found in. A task starts with a tool result whose `toolUseResult` holds a `backgroundTaskId`, or an `isAsync` agent launch with its `agentId`, written at or after the entry's `startedAt`. It ends with a `<task-notification>` naming its `<task-id>`, in a message or a queued input, a `task_status` attachment whose status isn't `running`, or a TaskStop or KillShell call whose result isn't an error, in whichever order the call and result were written. Sidechain records and `api-request-blob` copies are skipped, and at most 256 tasks are tracked per session. Each run reads only what the transcripts gained since the last one, in 65,536-byte chunks and at most 67,108,864 bytes across all listed sessions, parsing only lines that hold one of those records. A session whose transcript the budget stopped short of its end reports 0 until a later run finishes it, and a transcript that can't be read reports 0. A `thread` read of a listed session reads its transcript first, with its own 67,108,864-byte budget, so a task that started after the latest run counts at once. The counts are kept in memory and rebuilt after a restart.

`{ kind: 'session-states', afterSequence?, limit?, waitMs? }` returns state transitions in sequence order after `afterSequence` (default 0), at most `limit` per page (default 32, maximum 128), with `hasMore`; with `waitMs`, it waits for a transition, as [long-polls](#long-polls) describes. Continue after the last returned `sequence`. Each transition has `sequence`, `provider`, nullable `nativeId`, nullable `threadId` (managed sessions only), nullable `workspaceRoot`, `ownership`, nullable `previousState`, `state`, `reason` and `recordedAt`. `workspaceRoot` is the session's folder as the runtime knew it at the transition: a managed session's workspace, the one the runtime's first read of an observed Codex session found, or the resolved `cwd` the `claude agents --json` run listed an observed Claude session in; it is null when the runtime knew none. Every page also returns `latestSequence`, the highest sequence ever issued, or 0 before the first, so a reader can start after it to follow only new transitions, and `isReset`, true when the reader can't continue exactly after `afterSequence`: it is above `latestSequence`, as after a fresh state root or the restore of an older snapshot, or it is above 0 and its own transition was pruned. The page still holds the transitions after `afterSequence` that remain.

| Reason              | When                                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `opened`            | A session became idle without completing a turn: it was created, adopted, resumed or first observed idle.                               |
| `turn-started`      | A turn started.                                                                                                                         |
| `turn-completed`    | A running or waiting session became idle.                                                                                               |
| `waiting-for-input` | The session waits on an approval, a question or input.                                                                                  |
| `operator-stopped`  | An operator interrupt or close stopped a running or waiting managed session.                                                            |
| `failed`            | The session failed.                                                                                                                     |
| `disappeared`       | An observed session vanished while running or waiting, or the native connection or managed ownership was lost and its state is unknown. |
| `closed`            | An idle session closed.                                                                                                                 |

Transitions survive restarts. Each new transition deletes up to 128 transitions older than seven days, and closed observed sessions are forgotten after seven days. A managed session's stopping phase records no transition of its own.

`{ kind: 'active-sessions' }` returns every running and waiting session, managed and observed, and every idle session with `backgroundCommands` above 0, at most 128 and newest state change first, with `isTruncated` when more are active. Each comes as the summary `threads` returns, with its workspace root, name and timestamps. A managed session reads them from its managed record. An observed Claude session's workspace is the `cwd` the latest `claude agents --json` run reported, so it is left out until the first run after the runtime starts lists it; its name and timestamps come from its indexed transcript, and are null and its state's change time while the transcript isn't indexed. An observed Codex session's workspace, name and creation time come from its latest confirmed metadata, refreshed once on a `thread/name/updated` notification and when the shared connection rejoins the session. A renamed or cleared name updates that record without changing the activity time or appending a state transition. Its update time is its state's change time, and its native state and lineage are unknown. The read itself asks no provider anything. A session outside the allowed workspaces is left out.

`{ kind: 'observation-pace', pace: 'live' | 'background' }` sets the Claude poll to every 5 seconds or every 30, taking effect with an immediate run; the runtime starts at `background`. A host sets `live` while a client follows sessions live.

When the Codex daemon restarts, the runtime's connection ends: its sessions become uncertain, observed Codex sessions become unknown, and nothing is sent again. The provider reports unavailable until the next Codex read reconnects; recover uncertain sessions with `thread-recover`.

## Subscription observations

The usage metadata is optional, so a provider may omit it. Built-in adapters populate unknown metadata with null. Windows expose period (five-hour, seven-day or other), nativeKind, group and scope. Scope contains a nullable model with id/displayName and a nullable surface. Codex derives period from the actual duration; Claude normalizes recognized session and weekly groups to 300 and 10080 minutes. Primary/secondary remains the native position, not the period's identity. Existing bucket and window IDs remain stable.

credits contains independent bucket observations with hasCredits, isUnlimited and an exact nullable balance string. Its null value means unknown, never zero; do not add balances across buckets or assume a currency. resetCredits contains a nonnegative safe availableCount, independent of the provider's potentially capped reset detail list. Native account IDs and reset detail rows are not exposed. Credit/reset metadata can be available even when quota windows are unavailable; it grants no permission and provides no reset-redemption or purchase operation.

Codex prefers a valid nonempty rateLimitsByLimitId map and falls back to rateLimits when the map is absent, null or empty, without merging both views. A single rateLimits bucket without a native limitId uses `single` as its bucket ID. Missing or malformed optional credit/reset metadata becomes unknown while valid windows remain visible. Invalid quota-map content does not bypass boundary validation through the fallback.

Usage retains actual bucket/window identities, optional native labels, reported used percentage, remaining percentage, window duration and reset time. Percentages are never estimated from token counts or summed across sessions. Reported usage above 100 is preserved; remaining percentage floors at zero. `ordinaryUsageAllowed` is nullable when the native response does not report permission.

`available` means a usable observation exists. `exhausted` requires Codex's native permission/reached signal or a fully used Claude meter that the native response marks active. Neither label authorizes a model operation. `unavailable` covers missing windows or an observation that could not be obtained. Failed refreshes preserve a measured snapshot as `stale`, with its original `observedAt`. The complete prior observation, including credit/reset metadata and scopes, shares this freshness; an account change clears every field and invalidates responses started for the prior account. Observations older than 60 seconds or past a reported reset are stale. Codex account/rate-limit notifications trigger a coalesced refresh. Claude auth notifications discard account measurements and invalidate responses started for that account; rate-limit events mark the observation stale until the current or next structured refresh succeeds.

Claude uses the experimental `get_usage` control with `skip_behaviors: true`, and validates the native `rate_limits.limits` rows rather than inferring quotas from session costs or reading credentials. The [published provider control types](https://app.unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.301/files/sdk.d.ts) describe this protocol; the runtime invokes the installed CLI directly. Independent model/surface windows stay separate. Null percentages are omitted; zero is retained when reported. Unsupported shapes are unavailable. Claude does not report ordinary-usage permission, so it remains null. Recognized session and weekly groups have normalized five-hour and seven-day periods; unknown groups retain their native identity with period other and a null duration. No private OAuth endpoint, credential scrape or status-line execution is used.

Every Codex usage read requests current native observations. A Claude usage read is answered by the previous read's result, without asking Claude, until 60 seconds after that read finished; the freshness rules above still apply to it. An auth notification, a rate-limit event or a closed connection ends that minute early, and one that arrives during a read keeps its result from answering later reads. Otherwise the last successful snapshot is retained only to explain freshness after a failure. Multiple simultaneous reads share one pending refresh.

## Machine locks

`{ kind: 'locks' }` lists the named locks that scripts, agents and apps on this machine take through [jg-locks](https://jg-packages.jesusgraterol.dev/packages/jg-locks/), as jg-locks' `listLocks()` returns them: `{ data, isTruncated }`, at most 256 present locks sorted by name, with `isTruncated` when more exist. Each lock is `{ name, state, owner, isOwnerAlive }`, mirroring jg-locks' `ILockState`, and `LockStateSchema` and `LocksSchema` validate them. `state` is `held`, `owner-gone`, `ownerless`, `other-host`, `recovery-in-progress` or `unexpected-entries`, since free locks aren't listed. `owner` is `{ pid, nonce, hostname, program, cwd, startedAt, metadata }`, or null when its owner.json can't be read, and `isOwnerAlive` is null when there is no owner or it runs on another host.

The locks folder is `JG_LOCKS_ROOT` when it is set in the runtime's environment, otherwise jg-locks' default state folder, such as `~/.local/state/jg-locks` on Linux. A folder that doesn't exist yet holds no locks, and the read never creates it. The runtime only reads this folder: it never takes, waits for, releases or recovers a lock there, so recover a dead holder with `jg-locks recover <name> --nonce <nonce>`. The runtime's own locks in the state root, under [lock lifecycle](#lock-lifecycle), are separate. A `JG_LOCKS_ROOT` that isn't an absolute path fails with jg-locks' `LOCK_ROOT_INVALID`.

## CLI

`jg-agent-hq serve --state-root <directory> --workspace-root <directory>` starts the host. Repeat `--workspace-root` to authorize several roots. Client commands use `--state-root`; history commands also use one `--workspace-root` and, where required, `--native-id`. History and usage accept `--provider codex|claude` (default `codex`). Paged commands support `--limit` and `--cursor`; items support `--turn-id`. `jg-agent-hq threads` repeats `--workspace-root` for each folder and `--provider` for each provider, both by default, and accepts `--search`, `--exclude-continued`, `--limit` and `--cursor`. CLI paths resolve from the caller's working directory. There are no shell commands or raw native RPC passthroughs.

Output is one JSON line with `schemaVersion: 1`. Read output includes the command `kind` and `result`. Startup reports `kind: ready`. Confirmed shutdown reports `kind: stop` with `result.state: stopped`. Failure output goes to stderr with a safe error kind/message and exit status 1. The CLI never prints diagnostic causes or native payloads in an error response.

`jg-agent-hq session-states --state-root <directory> [--after-sequence <sequence>] [--limit <1..128>] [--wait-ms <1..30000>]` reads one page of session state transitions, and with `--wait-ms` waits for one. `jg-agent-hq active-sessions --state-root <directory>` reads the active sessions, `jg-agent-hq observation-pace --state-root <directory> --pace live|background` sets the Claude poll's pace, and `jg-agent-hq locks --state-root <directory>` lists the machine locks.

`jg-agent-hq request --state-root <directory>` reads one complete request from stdin, validates it, and prints the usual response. It accepts no extra target flags. This exposes action and reconnect operations, such as `action-wait`, without putting message text or question answers in command-line arguments. Its `stop` response acknowledges admission; use the dedicated `stop` command for confirmed shutdown.

## Browser host integration

`jg-agent-hq/contracts` exports closed `BrowserActionSchema`, `BrowserCommandSchema` and `BrowserReceiptSchema` contracts, plus `BrowserThreadDetailSchema`, a bounded view of one managed thread with its pending approvals, live items and recent actions. These schemas contain generic identities, not a deployment registry or private handler implementation. They do not expose native RPC, executables or provider configuration. Standalone IPC continues to support only its existing owned commands.

A trusted Node host calls `runtime.performBrowserAction(request, operatorId, execute)` after validating its signed operator identity. The host supplies one dispatcher function in process. It must validate every target against its registry, check operation-specific revisions/turns, and normalize approval provenance to that authenticated operator. Never accept a callback, operator identity or handler name from HTTP input. The request has a stable UUID, current runtime epoch and one closed command: native. The complete serialized request is limited to 2 MiB; nested native commands retain their tighter limits.

SQLite records an HMAC digest and receipt before invoking the dispatcher. The same UUID and identical normalized request returns the stored receipt without invoking it again. Changed payloads or operators conflict. New requests require the current epoch. Replaying a saved request after restart reconciles it without granting execution authority. Submitted receipts from another runtime become uncertain. Dispatcher failure also leaves the receipt uncertain because its effects may already have committed. This state never automatically resends an effect.

The dispatcher receives a server-owned `nativeActionId`; use this ID for a native child action, preserving the validated runtime and command. `readBrowserAction(id, operatorId)` returns only that operator's receipt and joins its exact native receipt. Host acknowledgement means the handler completed, not that a native turn completed. An unknown or differently owned ID returns null. Host receipts retain admission metadata rather than arbitrary handler output. The selected joined native receipt includes its queued input and complete bounded final result; paged domain reads omit those bodies. At most 32 host jobs are admitted concurrently. Runtime close rejects new host work and waits for admitted work before closing its worker.

Live reads accept `afterRevision`. A matching revision returns `unchanged: true` with an empty data array; retain the displayed window. A changed revision returns the complete bounded window. With `waitMs`, a matching revision waits for the next change. Revisions belong to one runtime. After reconnect to a new runtime, discard the revision and refresh native history. Token bodies stay in the existing bounded memory window and are never copied into lifecycle or browser-action tables.
